# 모바일·PC 조작, 선장 간 협력, 패치노트 상세 계획

- 작성: 2026-11-05 / 상태: **기본안 A/B 공개 배포 완료.** [실행과 확인 범위](UPDATE_2026-11-05_COASTAL_CREW.md).
- 통합 기준: [상위 개발계획](../DEVELOPMENT_PLAN.md), [개선 목록](../IMPROVEMENTS.md).
- 기존 항구 88곳·상품 23종·연안 항해·자동 구조·저장 이관 계획을 함께 적용한다. 중복된 새 게임이나 별도 서버를 만들지 않는다.
- 이 문서는 단계별 권장 범위를 구체화한다. 계획 작성 요청을 게임 배포나 미결정 보상 규칙의 승인으로 취급하지 않는다.

## 1. 범위와 우선순위

| 단계 | 구체적 범위 | 결정 상태 |
| --- | --- | --- |
| A · 통합 업데이트 기본안 | 모바일 하단 바로가기·교역창·큰 조종 버튼, PC 비교 화면·단축키, 즐겨찾기·상태 안내·화면 기억, 상단 패치노트 | 구현 기본안. 별도 제품 결정을 기다릴 항목 없음. |
| B · 가벼운 협력 기본안 | 선택한 항구/완료 항로 카드 공유, 주변 선장에 인사·감사·순항 기원 | 추가 공유 보상이나 무료 항구 해금 없이 기존 탐험·경제 규칙 유지. A와 같은 업데이트로 준비하는 권장안. |
| C · 공동 납품 | 여러 선장이 분담해 상품을 납품하는 공통 목표 | 아래 상세 제안과 저장 요건을 작성하되 도입 여부·목표·보상은 사용자 선택 전. 이번 기본 배포에 자동 포함하지 않음. |
| D · 동행 항해 | 초대와 수락 뒤 같은 목적지로 항해 | 아래 상세 제안. 자동 동행 도입 여부는 사용자 선택 전. 속도·수익 버프 없음. |

먼저 A+B와 기존 항해 개편을 구현·검증하는 순서를 권장한다. C/D는 상세안으로 남기며 사용자가 채택하기 전 코드·DB·공개 패치에 적용하지 않는다. 직접 화물/돈 송금, 개인 메시지, 길드, 전투, 강제 위치 공유는 이번 범위가 아니다.

## 2. 실제 불편과 설계 기준

현재 모바일의 지도 아래 순서는 조종 설정→항해 정보/랭킹/의뢰→지구본→항구 정보다. 교역까지 스크롤이 길고, 교역소 바로가기는 CSS에서 숨겨져 있다. 방향 버튼 38×37px·수량 버튼 36×36px 등 터치 영역도 작다. 거래할 때마다 별도 창이 닫혀 반복 동작이 많다. 새 버전 안내창은 있으나 상단에서 이력을 다시 여는 기능은 없다.

위 사항은 소스에서 확인했으며 실제 휴대폰의 오터치율·작업 시간은 측정하지 않았다. 다음 화면은 가독성·터치·저장 보호를 위한 구현 기본안이다.

- 해도 확대 배율은 고정, 미니맵은 지구본 유지.
- 현재 위치·정박지와 지도에서 선택한 항구를 항상 구분.
- 출항·거래·보급은 실제 게임 규칙으로 가능 여부를 계산. 화면만 버튼을 켜지 않음.
- 작은 지도 표식·드래그 외에도 항구 목록과 버튼으로 같은 기능 제공.
- 각 창은 첫 사용에 펼침. 사용자가 접은 뒤에만 그 선택을 기억. 자동 접기로 기존 결정을 바꾸지 않음.

## 3. 모바일 화면과 이동 동선

### 3-1. 기본 배치

850px 이하에서 다음 순서로 구성한다.

```text
상단: 게임명 / 접속 선장 / 업데이트 NEW
요약: 돈 / 화물+보급 공간 / 남은 보급
현재 행동: 정박지 또는 목적지·남은 시간 / 내 배
해도: 내 배와 주변 항구·시야
조작 구역: 자동·직접 / 큰 방향키·정지 (해도 밖)
하단 고정: 항해 | 항구·보급 | 화물 | 더보기
아래 정보: 펼쳐진 기존 정보창·지구본·랭킹·의뢰·채팅
```

하단 바로가기가 홈 표시줄·브라우저 도구줄과 겹치지 않도록 안전 영역과 동적 화면 높이를 반영한다. 360px 폭에서는 수치 단위와 버튼 문구를 줄여도 의미를 생략하지 않는다. 가로 화면에서는 지도 높이를 우선하고 중복 장식만 줄인다. 가로 스크롤이나 강제 화면 회전은 요구하지 않는다.

기존 정보창은 지도 아래에 펼쳐진 채 남긴다. 바로가기를 누르면 필요한 **같은 창**을 하단 패널로 옮겨 보여주고, 닫으면 원래 자리로 돌린다. 거래창을 복제해 서로 다른 수량·정박지를 보여주지 않는다. 이 패널의 열기/닫기와 내부 ‘접기/펼치기’는 별개다. 닫았다는 이유로 내부 창을 접힌 것으로 기록하지 않는다.

### 3-2. 바로가기 동작

| 버튼 | 동작 |
| --- | --- |
| 항해 | 패널을 닫고 지도·내 배로 복귀. 이전에 보던 지도를 유지하는 ‘둘러보기’와 ‘내 배 따라가기’를 명확히 구분. |
| 항구·보급 | 현재 정박지를 우선 열고 교역/보급/주점 선택. 다른 항구 시세를 보고 있었다면 선택 항구명과 ‘정박 항구로’ 버튼 표시. |
| 화물 | 현재 화물의 수량·매입 평균·정박지 판매가·예상 이익 표시. 항해 중이면 판매 불가 이유를 함께 표시. |
| 더보기 | 항구 찾기·지구본·랭킹·의뢰·채팅·일지·조작 설정으로 접근. 상단 업데이트는 여기로만 숨기지 않음. |

패널 기본 높이는 화면의 약 55%, 확장 시 최대 85%를 사용한다. 손잡이 드래그와 함께 확장/축소/닫기 버튼을 제공한다. 내부 목록의 스크롤과 패널 높이 변경을 혼동하지 않게 한다. 숫자 키보드가 열려도 선택 수량·총액·확정/닫기는 접근 가능해야 한다.

패널·대화창을 여는 순간 누른 방향키와 직접 이동 목표를 해제한다. 수동 이동은 닫아도 저절로 재개하지 않는다. 자동 항해는 기존 대화창처럼 열린 동안 날짜·보급 진행을 잠시 멈추고 닫으면 원래 진행 상태로 돌아간다. 사용자가 직접 일시 정지한 상태는 그대로 유지한다. 이 UI 정지는 보급 회복이나 항속 초기화가 아니다.

## 4. 지도·직접 조종·입항

- 모바일 방향 버튼은 기본 52×52 CSS px, 공간이 좁아도 48×48 이상. 중앙 정지와 내 배 버튼도 같은 크기. 왼손/오른손 선택에 따라 조작 구역의 순서를 바꾸고 배 위를 덮지 않는다. PC는 기존 방향키를 유지한다.
- 방향 버튼은 누르는 동안만 이동한다. 손을 떼기·버튼 밖 이동에 따른 캡처 종료·pointercancel·lostpointercapture·앱 전환·패널 열기에서 입력을 해제한다. 대각선은 같은 속도를 유지한다.
- 모바일 한 손가락 드래그는 해도 둘러보기다. 터치 이동량 10 CSS px를 드래그 판정의 초기값으로 삼고 실제 기기로 조정한다. 드래그·스크롤·다중 터치 뒤의 click을 항해 명령으로 처리하지 않는다. 두 손가락 동작으로 새 지도 확대 기능을 추가하지 않는다.
- **항구 터치:** 선택 표시와 지도 밖 행동 카드만 표시. 거리·예상 일수·보급·입항 여부를 보고 큰 ‘여기로 항해’ 버튼으로 출항한다. 작은 표식에 못 맞추면 알려진 항구 목록에서 똑같이 선택할 수 있다.
- **모바일 바다 터치:** 자동 모드는 경로 미리보기→출항, 직접 모드는 목표 표시→‘여기로 이동’ 확정. PC의 바다 클릭 직접 이동은 유지한다. 직접 이동 중 다른 곳을 끌어 둘러봤다고 목표를 바꾸지 않는다.
- 직접 입항 판정은 기존 구간·수로·육지 검사와 상위 계획을 따른다. 입항 완료 시 실제 항구명과 ‘교역 가능’을 강조하고 하단 항구 버튼을 활성화한다. 거래창을 강제로 열거나 지도를 이동시키지 않는다.
- 선장 배 선택은 시야 안에서만 가능하다. 항구/배/바다 선택이 겹치면 선택 가능한 대상 목록을 표시해 임의로 출항시키지 않는다. 배 표식은 정보 읽기·신호 전송용이며 상대 위치로 자동 추종하지 않는다.

## 5. 교역·보급을 한 화면에서

### 5-1. 표시와 수량 선택

구매/판매 탭은 같은 거래 화면에서 전환한다. 상품마다 단가·공급 역할(P/L/I/수요)·보유량·매입 평균·현지 판매 시 상자당 손익을 표시한다. 전체 선택 수량·총액·거래 후 돈·보급 포함 사용 공간은 하단 확정 영역에 둔다. 손해 거래는 색상만 아니라 ‘예상 손실’ 문구로도 알린다.

수량은 −1/+1 버튼과 1/5/10/최대 프리셋을 제공한다. 숫자 입력은 눌렀을 때만 키보드를 열고 정수만 확정한다. 기본 수량은 1이다. 상품을 바꿔도 이전 상품의 최대 수량을 자동 거래하지 않는다.

‘최대’는 현재 보유 보급을 유지한 채 가능한 수량이다. 별도의 **‘보급 여유를 남기고 최대’**는 선택 항로의 필요량+예비량, 항로가 없으면 선박의 최대 보급을 기준으로 공간과 향후 보급 비용을 남긴다. 비용은 현금으로 실제 더 필요한 보급만 계산하고 보급 크레딧을 먼저 반영한다. 이는 수량 제안일 뿐 자동 보급 구매가 아니다. 총액 옆에 ‘보급비 XX D와 YY칸 남김’을 표시한다.

판매는 지도 선택과 관계없이 실제 정박지 가격이다. 다른 항구 시세와 섞지 않는다. 입항 상태·보유금·화물·보급이 바뀌면 확정 직전에 다시 검증한다. 적재 초과 이관 저장도 화물을 팔고 보급을 내릴 수 있어야 한다.

### 5-2. 연속 거래와 실수 방지

확정 후 창 전체를 닫지 않고 해당 상품 목록과 스크롤을 유지한다. ‘와인 5상자 판매·총액·매입원가 대비 이익’을 짧게 알리고 수량과 잔고를 갱신한다. 다음 거래는 새 선택/확정 동작으로만 발생한다. 전송 중 연속 탭과 Enter 반복은 같은 작업을 두 번 처리하지 않는다.

자금·화물·원가·거래 로그는 기존 계정 저장 한 건의 상태 변경으로 기록한다. 서버 저장 실패 시 이미 기기에 반영한 거래를 다시 실행하지 않고 미전송 저장으로 보존한다. 클라우드 완료와 기기 저장·재연결 대기를 구분한다. 금전 거래를 되돌리는 임의 Undo나 자산을 자동으로 팔아 보급하는 기능은 추가하지 않는다.

첫 구현에는 ‘화물 전체 판매’를 넣지 않는다. 상품별 최대 판매로 충분히 조작을 줄이며, 여러 품목을 한꺼번에 파는 기능이 필요하면 품목별 가격·원가·총액을 확인하는 별도 계획으로 다룬다.

## 6. PC·공통 탐색과 설정

### 6-1. PC 레이아웃과 키보드

1200px 이상은 왼쪽 정보·중앙 지도·오른쪽 항구/화물 비교의 3영역을 유지한다. 오른쪽 폭은 280~420px에서 조정하고 ‘좁게/기본/넓게’ 버튼도 제공한다. 지도 폭 480px을 침범하면 더 넓히지 않는다. 851~1199px은 지도+오른쪽의 2영역으로 배치하고 보조 정보는 아래로 옮긴다. 창 본문은 자동으로 접지 않는다. 850px 이하는 모바일 바로가기를 사용한다.

| 키 | 동작 | 적용 범위 |
| --- | --- | --- |
| 방향키 / WASD | 직접 조종 | 해도에 키보드 초점이 있을 때 |
| Space | 직접 정지 / 자동 일시 정지·재개 | 해도 초점, 또는 전용 조작 버튼에 안내된 동작 |
| H | 내 배로 돌아오기 | 해도 초점 |
| T / B | 교역 / 보급 열기 | 해도 초점 |
| U | 업데이트 열기 | 해도 초점 |
| Esc | 맨 위 패널/대화창 닫기, 없으면 직접 이동 정지 | 입력기의 조합 중 Esc는 가로채지 않음 |

채팅·수량·검색·contenteditable·IME 조합 중에는 항해 단축키를 무시한다. Ctrl/Alt/Meta 조합과 브라우저 단축키를 가로채지 않는다. 글자 단축키는 설정에서 끌 수 있고 버튼에도 대안이 있다. Enter는 초점이 있는 버튼의 동작만 수행하며 전역 거래 확정 키로 쓰지 않는다. 대화창을 닫으면 연 버튼으로 초점을 돌린다.

### 6-2. 현재 행동·즐겨찾기·화면 기억

- 상태줄은 정박 항구 / 자동·직접·구조 중 / 목적지 / 남은 게임 일수와 활성 항해 시간 / 보급 여유를 문맥에 맞게 보여준다. 구조 중에는 실제 비용 지불 여부를 보여주되 다른 선장에게 금액을 공개하지 않는다.
- 알려진 항구에만 즐겨찾기(최대 20개)·최근 입항(8개)·이름 검색·거리순을 제공한다. 즐겨찾기에는 현재 배로 출항 가능한지 표시하며, 가까움과 안전한 도달 가능성을 혼동하지 않는다.
- 즐겨찾기와 최근 항구는 본인 저장에 추가한다. 새 기록은 빈 즐겨찾기와 리스본 최근 기록, 기존 기록은 현재 정박 항구만 확실한 최근 기록으로 이관한다. 과거 방문 배열을 실제 최근 입항 시간인 것처럼 변환하지 않는다.
- 접기 상태·오른손/왼손·PC 영역 폭·글자 단축키 설정은 계정별 기기 키 `windward-ui-v1:{uid}`에 저장한다. 모바일·PC 폭 설정을 분리한다. 초깃값은 모든 창 펼침, 오른손, 기본 폭이다. 설정 초기화는 이 UI 키만 정리하고 게임 저장을 지우지 않는다.
- 핵심 알림은 키보드 초점을 뺏지 않는 상태 영역에 표시한다. 보급 위험·입항·저장 실패는 다음 행동을 찾을 때까지 다시 볼 수 있고, 거래 성공은 짧게 표시한다. 경고를 매 프레임 반복하거나 오류마다 대화창을 쌓지 않는다.

## 7. 상단 업데이트와 지난 패치 보기

### 7-1. 이용자 동작

- PC·모바일 상단에 **업데이트** 버튼을 항상 둔다. 최신 공개 버전을 읽지 않았으면 작은 NEW 표시를 붙인다. 좁은 화면에서도 상단의 짧은 라벨로 접근한다.
- 눌러 열면 최신→이전 버전 목록, 날짜·버전·요약과 ‘새 기능 / 조작 개선 / 항해·교역 조정 / 오류 수정’을 표시한다. 과거 패치에는 현재 규칙과 다를 수 있음을 짧게 알린다.
- 첫 접속 새 버전 안내는 핵심 변화만 요약하고 ‘자세히’와 ‘확인하고 항해’를 둔다. 매 접속마다 강제로 긴 이력을 읽게 하지 않는다. 기존 초기화 안내를 새 업데이트에도 복사하지 않는다.
- 닫기만 하면 기존처럼 읽음으로 저장하지 않는다. 최신 버전의 **확인**을 누를 때 `accounts/{uid}/seenVersion`을 한 번 기록한다. 과거 이력 보기와 열기/닫기만으로 서버 쓰기를 하지 않는다.
- 최신 확인 중 서버 연결이 끊기면 기기에 확인 대기 상태를 남기고 계정 연결 회복 시 같은 최신 버전만 재시도한다. 서버에 이미 읽은 버전은 중복 쓰지 않고, 예전 버전의 늦은 재시도로 더 최신 읽음 기록을 뒤로 돌리지 않는다.
- 창을 닫아도 지도·선택 항구·거래 수량·스크롤·접기 상태를 복원한다. 게임 진입 전에도 공개 이력은 읽을 수 있지만 다른 계정의 읽음 기록으로 합치지 않는다.

### 7-2. 단일 원본과 공개 기준

신규 `docs/releases.json`을 원본으로 날짜·고유 release ID·제목·요약·분류별 항목·published 여부를 관리한다. 생성 도구 `tools/build-release-notes.mjs`가 공개용 `dist/release-notes.js`와 `CHANGELOG.md`를 만든다. 현 CHANGELOG의 과거 8개 항목은 버리지 않고 이관하고 실제 과거 버전 식별자는 확인 가능한 것만 사용한다.

`RELEASE`와 게임의 최신 안내도 생성된 공개 데이터에서 가져온다. 아직 구현하지 않은 항구·보급·협력 기능은 published 목록에 넣지 않는다. 문서만 작성한 날짜를 게임 업데이트 날짜로 표시하지 않는다. 최신 버전 식별자는 날짜 문자열의 사전순 대신 공개 목록의 명시적 순서로 비교한다.

`--check` 모드는 원본과 생성물 불일치·중복 ID·잘못된 날짜·미배포 항목 혼입을 검사한다. 향후 `npm run notes:check`와 Pages 검증 단계에 추가한다. 이번 계획 단계에는 생성 도구나 배포 데이터를 만들지 않는다. 표시에는 HTML 삽입 대신 안전한 텍스트 렌더링을 사용한다.

## 8. 정보 공유와 인사 · B 기본안

### 8-1. 항구·항로 카드

방문한 항구의 ‘정보 공유’를 누르면 전송 미리보기 후 본인이 보내기를 누른다. 항구 이름·해역·대표 상품·항구 이야기 링크를 같은 전체 채팅에 공유한다. 전체 화물·보유금·현재 배 좌표·탐험 지도를 자동 첨부하지 않는다. 게임이 자동으로 축하나 공유 메시지를 보내지 않는다.

받는 사람이 이미 알고 있는 항구는 정보와 현재 배 기준의 새 항해 미리보기를 연다. **미개방 항구는 지명·상품 이야기 단서만 볼 수 있고, 수신만으로 knownPorts/visited/탐험 안개를 변경하지 않는다.** 항로 지정과 정식 해금은 기존 접근 발견·주점 정보 규칙을 따른다. 별도 정보 공유 보상은 없다. 이 기본값으로 핵심 탐험 보상을 임의 변경하지 않는다.

출발·도착이 실제 항구로 확인된 최근 완료 항로만 최대 5건을 개인 저장에 두고, 출발/도착 항구 ID와 관측 거리만 공유할 수 있다. 바다 좌표에서 시작하거나 끝난 이동을 임의의 항구 간 기록으로 만들지 않는다. 해도 전체 폴리라인이나 선장의 현재 위치는 전송하지 않는다. 받는 사람은 두 항구를 알고 있어야 목적지로 사용할 수 있고, 수신한 거리·보급을 그대로 실행하지 않고 자기 배·보급·현재 위치에서 경로를 다시 계산한다.

시세는 각자의 게임 날짜에 따라 달라진다. 첫 카드 버전은 실시간 가격을 포함하지 않는다. 향후 가격 관측을 붙인다면 관측 선장·게임 날짜·관측 시점·‘현재 내 시세와 다를 수 있음’을 함께 표시하는 별도 개선으로 다룬다.

### 8-2. 간단한 신호

시야 180해리 안의 다른 배를 누르거나 그 배의 목록 대안을 선택해 ‘안녕하세요 / 고마워요 / 순항하세요’를 보낸다. 전송 미리보기에서 전체 채팅에 보이는 메시지임을 알린다. 상대 이름을 포함하되 개인 메시지라고 소개하지 않는다. 시야 밖 이름은 기존 접속 명단에서 보이더라도 지도 위치나 신호 대상을 새로 추적하지 않는다.

간단한 신호도 기존 채팅의 3초 전송 제한과 최근 50개 보관에 포함한다. 별도 영구 인사 기록·호감도·현금 보상·추가 위치 방송은 없다. 메시지 클릭이 즉시 출항·거래를 실행하지 않는다.

### 8-3. 채팅 형식과 보안

기존 `text`는 200자 이하의 대체 문구로 항상 유지한다. 새 선택 필드 `kind`와 `ref`로 다음 종류를 표현한다. 선택 필드가 없는 기존 글은 일반 텍스트다.

| kind | ref 허용 필드 | 처리 |
| --- | --- | --- |
| text 또는 생략 | 없음 | 기존 대화 |
| port | portId | 유효 항구 ID, 카드의 설명·상품은 정적 데이터에서 읽음 |
| route | fromPortId, toPortId, observedNm | 출발/도착 ID와 0~100,000 범위 관측 거리. 실제 항해는 재계산 |
| signal | code, targetUid, targetName | 고정 신호 3종, 대상 uid 길이 제한·이름 1~16자. 발신자는 기존 auth.uid |

카드·신호도 기존 순번/50자리 덮어쓰기/서버 시각/발신자 권한/3초 제한과 한 원자 쓰기로 처리한다. kind별 불필요한 필드·좌표·임의 HTML·임의 경로 데이터는 거부한다. 항구 ID는 게임 데이터에서 생성한 허용 목록으로 검사한다. 행 전체를 새 메시지로 교체해 이전 카드 메타데이터가 남지 않게 한다.

카드가 본인이 실제로 방문했다는 사실이나 관측 거리는 클라이언트의 공유 정보다. 현재 비공개 진행은 JSON 문자열이므로 서버 규칙이 방문 이력을 파싱·증명한다고 주장하지 않는다. 상대 배의 시야 판정도 기존처럼 클라이언트의 표시·조작 제한이며 서버가 선장 간 실제 거리를 엄격히 검증하는 새 보안 경계를 뜻하지 않는다. 직접 변조한 앱까지 완벽히 검증하는 경쟁 서버로 바꾸지 않는다. 공유만으로 보상·해금·상대 저장 변경이 발생하지 않게 하여 기본안의 자산 일관성을 유지한다.

카드 표시 실패 시 text를 보여준다. 오래된 클라이언트의 일반 글과 새 카드가 같은 50자리를 사용할 수 있어야 한다. 새 규칙을 먼저 배포하고 클라이언트를 전환하며 기존 메시지는 삭제하지 않는다.

## 9. 공동 납품 · C 후속 선택안

### 제안하는 경험과 숫자

선택 예시는 **세투발에 모직물 총 40상자 납품**이다. 접속 시간이 달라도 실제 입항한 선장이 1~보유량 범위에서 기여한다. 강제 참가·접속 인원 조건은 없고 소수 접속이어도 완료할 수 있다. 1차 시범은 활성 목표 1개·시간제한 없는 단일 의뢰로 제안한다. 자동 시즌·매일 리셋·미참여 강제 알림은 만들지 않는다.

각 납품은 정상 판매처럼 상품을 차감하고 그 선장의 현지 판매가로 정산한다. 목표를 넘는 마지막 기여는 남은 수량까지만 인정한다. 별도 완료 보상은 **총 400 D를 실제 기여 수량 비율로 분배**하는 안을 제안한다. 40상자 기준 상자당 10 D여서 나머지 반올림 문제가 없다. 이 보상은 무역 이익 순위에 넣지 않는 협력 보상이다. 기여 0이면 지급하지 않고 혼자 완수했다면 혼자 받는다. 공동 참여자 명단으로 실제 분담은 확인할 수 있다.

이는 제품 규칙의 **추천 수치**이며 아직 채택된 규칙이 아니다. 도입 여부·실제 목표와 보상은 사용자 선택 뒤 확정한다. 게임 날짜가 이용자마다 다르므로 목표를 개인의 항해 날짜로 만료시키지 않는다. 후속 기간제를 도입한다면 공통 실제 시각을 기준으로 별도 설계한다.

### 저장·동시성 선행 요건

- 화물 차감·판매 정산·기여 누적·목표 잔량과 완료 판정이 함께 성공하거나 함께 실패해야 한다. ‘개인 저장 후 공통 목표 저장’ 같은 분리 쓰기는 사용하지 않는다.
- 기존 개인 게임 데이터는 JSON 문자열이므로 RTDB 규칙이 수량·현금 증감을 직접 검증하기 어렵다. 이 기능을 채택하면 구조화된 경제 필드와 이관 방식을 먼저 확정한다. 단순 UI 확인만으로 공정한 공동 자산 처리를 보장하지 않는다.
- 개인 revision과 목표 revision 비교를 포함한 필요한 경로만의 원자 업데이트를 설계한다. 충돌 시 최신 개인 저장·해당 목표만 다시 읽고 사용자가 제출한 수량 범위 안에서 재계산한다. 전체 `gameV2` 트랜잭션/다운로드로 해결하지 않는다.
- 납품 operation ID와 계정별 완료 보상 수령 ID를 보존해 이중 클릭·두 창·통신 단절·실패 후 재시도에서 중복 차감/지급을 막는다. 납품 서버 성공이 확인되기 전 성공 보상을 보여주지 않는다.
- 공유 목표에는 공개 진행과 게임용 선장 이름·기여량만 저장한다. 다른 사람의 전체 개인 저장을 읽게 하지 않는다. 원가·지갑·화물의 공개 복제는 금지한다.
- C는 본인 JSON 저장 이관보다 큰 변경이므로 구조화된 필드, 권한, 원자 정산·재접속 복구를 별도 에뮬레이터 검증한 뒤 배포한다. A/B를 먼저 적용할 때 공동 목표 경로를 미리 열어두지 않는다.

## 10. 동행 항해 · D 후속 선택안

같은 항구에서 같은 목적지를 고른 선장끼리 초대하고 수락한다. 추천 기본값은 최대 4척이다. 출발 전에 각자의 배로 경로·보급·예비량·연안 한계를 만족하는지 확인한다. 한 명의 원양선이 다른 연안선의 통과 금지를 없애지 않는다.

출발 후에는 같은 정적 경로를 각자 계산하며 가장 느린 참여 선박 속도를 적용한다. 보급은 각자 실제 경과 일수만큼 사용한다. 추가 속도/수익 보너스·강제 좌표 추종·자동 보급 양도는 없다. 참가하지 않은 다른 선장에게 시야 밖 좌표를 공개하지 않는다.

누구나 동행을 나갈 수 있고 선두 이탈·접속 종료 시 나머지는 마지막 합의 경로를 각자 이어간다. 상대가 오프라인이라고 강제로 기다리지 않는다. 내 보급 소진은 기존 자동 구조를 우선하고 동행에서는 이탈한다. 재접속해도 상대를 따라 순간 이동하거나 자동 재가입하지 않는다.

초대·수락·이탈·목적지 변경만 공통 상태로 동기화하는 안을 우선한다. 별도 고빈도 위치 방송을 추가하지 않는다. 구현 채택 시 초대 만료·이탈 기준·진행 속도 변경을 최종 정하고, 미수락 이동 금지와 개인 위치·보급 복구를 검증한다. 이 단계의 자동 동행은 아직 도입 승인 전이다.

## 11. 저장·비용·개발 파일

### A/B의 데이터 원칙

`gameV2`·Google 계정·기존 저장 이관을 유지한다. 즐겨찾기(20)·최근 항구(8)·최근 완료 항로(5)만 본인 저장에 추가하고 없는 기록은 빈 값으로 이관한다. 화면 설정은 해당 기기에 저장한다. 개인 설정을 바꿀 때마다 Firebase 전체 저장이나 계정 프로필 쓰기를 즉시 반복하지 않는다.

패치 이력과 상품 설명은 정적 파일로 읽고 추가 실시간 구독을 만들지 않는다. 카드와 신호는 기존 chat 경로와 보관량을 재사용한다. 메타데이터로 글 한 건의 크기는 늘 수 있으므로 실제 총 전송량 0원은 보장하지 않는다. C/D를 선택하면 공유 목표/동행 상태 쓰기가 추가되므로 그 단계에서 필요한 경로만 제한 조회하도록 설계한다. 기존 Spark와 Pages를 유지하며 새 유료 서비스·AI API·Cloud Functions는 이 기본안에 필요하지 않다.

## 12. 순서와 완료 기준

1. 기존 데이터 이관·항해 규칙 기반을 만든 뒤 UI 상태/입력 경계를 분리한다. 모바일과 PC가 거래·항해 규칙을 각각 복제하지 않게 한다.
2. 하단 바로가기·패널·큰 조작 버튼·PC 레이아웃을 구현하고 실제 입항/교역 동선을 먼저 확인한다.
3. 공통 거래 화면·보급 여유 최대·즐겨찾기·설정을 붙인다. 상품 23종과 과적 이관 사례를 함께 확인한다.
4. 패치 원본·생성 도구·상단 버튼·기존 읽음 기록을 연결한다. 실제 출시 기능만 공개 목록에 넣는다.
5. B 메시지 형식과 규칙을 에뮬레이터에서 검증하고 정보 공유·신호를 붙인다. C/D 경로는 열지 않는다.
6. 상위 계획의 전체 항해/경제/저장 검증과 함께 A/B를 확인한다. 동작 검증 후 규칙을 먼저 호환 확장하고 Pages를 배포하며, 상위 계획의 schema 2 최종 전환을 따른다.
