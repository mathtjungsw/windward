# 바람의 항로 상세 개발계획 · 현실 시간으로 움직이는 공동 시장

- 작성일은 2026-11-06이다.
- 상태는 **상세 계획 완료 · 구현과 배포 대기**다.
- 사용자가 요청한 범위는 반복 구매 시 상승, 반복 판매 시 하락, 시간 경과에 따른 원상 회복, 모든 시세 계산의 현실 절대시간 적용이다.
- 아래 수치와 서버 공통 시장은 추천 기본안이다. 사용자가 확정한 수치로 표현하지 않는다. 이후 업데이트 실행 지시가 오면 이 기본안으로 개발하고 검증 중 조정이 필요하면 근거를 남긴다.
- 대상은 기존 `windward`, Google 로그인, 현실서버, Firebase `windward-voyage`, GitHub Pages다.
- 앞선 세계 탐험·선단 계획은 [이전 계획](plans/DEVELOPMENT_PLAN_2026-11-06_WORLD_FLEET.md)에 보존한다. 이번 계획은 [개선 목록](../IMPROVEMENTS.md)의 공동 시장 항목을 구체화한다.

## 1. 완료 후 플레이 경험

A항구에서 와인을 많이 사면 A항구 와인 가격이 점차 오른다. B항구에 같은 와인을 계속 팔면 B항구 와인 가격이 내려간다. 반복 왕복의 이익이 줄면 다른 상품이나 항구를 찾아보게 된다. 실제 시간이 지나면 각각의 항구 가격은 기준 수준으로 회복한다.

같은 서버의 선장들은 항구·상품별 시세를 공유한다. 다른 선장의 거래도 같은 시장에 반영되는 방식이 추천안이다. 항해 일수, 게임 속 연도, 선박 속도와 관계없이 같은 순간의 같은 상품은 같은 시장 상태를 사용한다. 로그인하지 않은 동안에도 회복 시간이 흐른다.

교역소에는 현재 매입·매도 가격과 함께 ‘매수 증가 +8%’, ‘물량 증가 −12%’, ‘추가 거래가 없으면 약 8분 후 정상’처럼 거래 효과와 회복 전망을 표시한다. 실제 거래 전에 수량 전체의 총액과 평균 단가를 보여준다.

## 2. 현재 구현과 변경점

현재 `dist/engine.js`의 `price(portId, goodId, day)`는 지역 공급·수입 계수와 개인 게임 날짜의 7일 구간으로 시세를 계산한다. 거래 수량에 따른 가격 압력은 없다. `sellPrice`는 계산된 가격의 88%를 내림한다. `buy`와 `sell`은 기기의 게임 상태를 먼저 바꾸고 일반 자동 저장으로 서버에 보낸다.

`dist/ux.js`의 수량 확인 창과 최대 구매도 이 동기식 계산을 사용한다. 현재 저장 봉투는 v4이고 게임 데이터는 v3이며, 계정별 revision·세션 인계·기기 백업이 있다. 공개 순위는 개인 저장 확인 뒤 갱신된다.

공동 시세를 도입하면 시세 조회, 구매·판매 견적, 거래 확정, 자동 저장을 함께 연결해야 한다. 시장 가격만 따로 갱신하고 자금·화물을 나중에 저장하는 방식은 중간 실패에 취약하므로 거래 단위로 일치시킨다.

## 3. 추천 수치

| 항목 | 추천 기본안 | 플레이 의미 |
| --- | --- | --- |
| 기준 가격 | 상품 기본가 × 항구별 기존 공급·수입 계수 | 지역 특산물과 교역 차이를 유지 |
| 공통 기준 시세 변동 | 현실 24시간 주기, ±4.5% | 모든 선장이 같은 시계 사용 |
| 한 상자 구매 | 가격 압력 +0.1%p | 구매가 누적될수록 상승 |
| 한 상자 판매 | 가격 압력 −0.1%p | 공급이 누적될수록 하락 |
| 거래 가격 압력 범위 | 기준 시세 대비 −30%~+30% | 폭등·폭락 범위를 제한 |
| 자연 회복 속도 | 현실 1분에 1.5%p씩 0으로 접근 | 최대 변동에서 20분 후 정상 |
| 매도 환산율 | 같은 상태의 매입 기준가 × 88% | 매입·매도 가격 차이 적용 |
| 견적 유효 시간 | 최대 5초, 시장 revision 변경 시 재확인 | 확인한 금액으로 체결 |
| 한 번의 수량 | 정수 1~1,000상자, 적재·자금·보유량 추가 검사 | 최대 선단 적재 범위 수용 |

거래 압력만 0으로 회복하며 기준 시세의 현실 시간 변동은 계속된다. 따라서 ‘정상’은 당시 기준 시세를 뜻한다. UTC 기준일을 `2026-11-06T00:00:00Z`로 고정하고 모든 시점은 UTC 밀리초로 계산한다. 화면에서는 이해하기 쉬운 한국어 시간·분 표시를 쓴다.

회복 중 반대 거래를 하면 먼저 압력을 상쇄한다. 예를 들어 구매 때문에 +10%인 곳에서 같은 상품 100상자를 팔면, 시간 경과가 없는 계산에서는 0%가 된다. 그 뒤 추가로 팔면 음수가 된다. 상·하한에서도 거래는 가능하며 가격 압력은 한도 안에 머문다.

| 추가 거래가 없는 경우 | 정상까지 걸리는 현실 시간 |
| --- | --- |
| 20상자로 발생한 ±2% | 1분 20초 |
| 100상자로 발생한 ±10% | 6분 40초 |
| 최대 ±30% | 20분 |

위 표는 압력 0에서 시작한 예시이며 기준 가격의 작은 주기 변동은 별도로 계산한다.

## 4. 가격 계산 명세

### 기준 가격과 현실 시계

1. 기존 항구의 생산·지역 공급·수입·수요 역할에서 지역 기준가를 계산한다.
2. 항구·상품의 고정 위상과 UTC 시간을 사용해 ±4.5%의 연속적인 24시간 주기 변동을 적용한다. 날짜 경계에서 한꺼번에 가격이 뛰지 않게 한다.
3. 동일 시점의 입력에 대해 결정적인 값을 내도록 카탈로그의 고정 ID/위상과 `marketVersion`을 사용한다. 배열 순서에 따라 시세가 바뀌지 않게 한다.
4. 매입·매도·비교 가격·관측 시각·회복 표시에서 개인 게임 날짜를 제거한다.

서버가 저장한 거래 시각과 서버 보정 시계를 사용한다. 서버 시간 차이를 처음 연결할 때 확인하고 재연결·탭 복귀 시 갱신한다. 연결 중에는 마지막으로 동기화한 서버 시각과 단조 증가 타이머의 경과를 조합해 기기 시계 변경 영향을 줄인다. 서버 규칙의 `now`를 최종 거래 시각 검사에 사용한다.

### 압력과 회복의 고정 소수점 계산

정수 단위로 100%를 4,000,000으로 표현한다. 한 상자는 4,000, 압력 한도는 ±1,200,000, 회복량은 현실 1밀리초당 1이다. 이 방식이면 시간에 따른 회복을 정수 덧셈·뺄셈으로 처리할 수 있다.

저장 압력을 P, 서버의 마지막 반영 시각을 T, 계산 시각을 t라 한다. 경과 시간은 `max(0, t−T)`이다. P가 양수면 경과량을 빼되 0 아래로 내려가지 않고, 음수면 경과량을 더하되 0 위로 올라가지 않는다. 정상 도달 후에는 0을 유지한다.

조회할 때는 회복된 값을 계산해서 보여준다. 실제 거래가 성공할 때만 현재 압력과 새 서버 시각을 기록한다. 소수의 상자로 나누어 사고팔아도 같은 시점·순서라면 같은 압력 궤적이 되게 한다.

### 대량 거래와 반올림

- 선택 수량 q의 각 상자 j에 대해 그 상자가 거래되기 직전의 압력으로 단가를 계산한다. 거래 방향에 맞춰 다음 상자의 압력을 올리거나 내리고 매 상자마다 한도를 적용한다.
- 구매 단가는 기준 시세에 압력 계수를 곱한 뒤 정수 두카트로 올림한다. 판매 단가는 같은 계산에 0.88을 곱한 뒤 내림한다. 구매는 최소 1 D, 판매는 최소 0 D로 정의한다.
- 총액은 각 상자의 정수 단가를 합산한다. 평균 단가는 표시용이며 표시 반올림값에 수량을 곱해 결제하지 않는다.
- 거래 시작 시각 하나를 수량 전체에 사용한다. 처리 중 시계가 바뀌거나 코드가 늦어져도 총액이 흔들리지 않게 한다.
- 같은 시점에 100상자를 한 번에 거래한 결과와 10상자씩 10번 거래한 결과의 압력·총액은 일치해야 한다. 실제 시간이 지났거나 다른 사람이 거래하면 새 견적을 사용한다.
- ‘최대 구매’는 모든 상자의 가격 변화를 합산해 자금·보급 여유·적재 한도를 만족하는 최대 정수를 계산한다. 기존 `현재 단가로 자금 나누기` 계산을 교체한다.

가격이 낮은 상품은 정수 반올림의 영향이 크다. 구현 검증에서 초반 교역 수익과 함께 확인한다.

## 5. 거래 견적과 사용자 조작

교역소를 열면 선택한 항구의 필요한 상품만 읽는다. 상품을 선택하면 거래 전 가격, 수량 전체 총액, 평균 단가, 거래 뒤 예상 가격, 거래 뒤 자금·적재량을 표시한다. ‘1 / 5 / 10 / 최대’와 보급 여유를 남기는 구매 방식을 연결한다.

수량을 바꾸면 최신 시장 상태와 현재 서버 보정 시각으로 다시 견적을 낸다. 회복 시계는 화면에서 초 단위로 갱신하되 표시를 위해 DB를 반복 읽지 않는다.

다른 선장의 거래나 견적 유효 시간 만료로 금액이 달라지면 확정 버튼에서 새 견적과 ‘시세가 바뀌었어요. 금액을 다시 확인해 주세요’를 보여준다. 더 비싼 금액으로 자동 체결하지 않는다. 새 금액에 다시 동의해야 거래한다.

연결되지 않거나 거래 결과가 확인되지 않은 동안 구매·판매 확정 버튼을 잠그고 재연결 상태를 표시한다. ‘처리 중 → 거래 완료 → 최신 가격 표시’ 흐름으로 진행하며 결과가 불명확하면 ‘거래 결과 확인 중’으로 남겨 서버 기록을 다시 읽는다.

항구의 수요 설명과 함께 방문 도시·지도 탐험·선단 UI가 좁은 모바일 화면에서 읽히는지 확인한다. 새 안내는 내용 높이에 맞춘 기존 짧은 알림을 사용한다.

## 6. 적용 범위와 호환 동작

- 교역품의 항구별 구매·판매와 항구 비교 시세에 공동 시장을 적용한다.
- 보급·선박 개량·선박 추가·구조비는 현재 가격 체계를 사용한다. 이번 시세 변경의 추천 적용 범위를 교역품으로 정한다.
- 혼합 향신료 같은 구버전 판매 전용 화물과 과거 항구에 정박한 저장도 처리한다. 판매만 가능한 조합은 시장 상태를 필요할 때 생성하고 구매 가능 목록을 늘리지 않는다.
- 거래로 올리거나 내린 가격을 항구 정보 공유에 표시할 때 서버 관측 시각을 함께 남긴다. 과거 공유 카드의 가격은 당시 관측값으로 표시한다.
- 화물별 매입 원가, 부분 판매의 원가 배분, 무역 이익, 첫 교역 의뢰의 계산을 새 실제 체결 총액과 연결한다. 압력만 바꾸는 거래와 보상만 따로 지급되는 실패 경로를 막는다.

## 7. 공동 시장 저장과 거래 일관성

### 필요한 데이터

| 경로·구조 | 저장 내용 | 읽기 범위 |
| --- | --- | --- |
| `gameV2/marketV1/items/{portId}/{goodId}` | pressureUnits, revision, updatedAt, 마지막 거래 식별 정보 | 선택 항구의 필요한 상품 |
| `gameV2/privateSaves/{uid}` | 기존 JSON 진행·revision·세션에 tradeSequence와 마지막 거래 결과 추가 | 본인 기록 |
| 본인 기기 거래 대기 기록 | 거래 ID, 순번, 예상 revision, 수량, 승인 총액 | 본인 기기 |

시장에는 자금·화물·이메일을 저장하지 않는다. 이 값들은 본인의 비공개 진행 기록에 속한다. 원본 거래 이력 전체 대신 시장 상태와 마지막 반영 정보, 본인의 단조 증가 거래 순번을 사용한다.

### 확정 순서

1. 계정의 저장 대기 작업이 끝난 뒤 거래 쓰기 잠금을 얻는다. 현재 자금·화물 스냅샷은 잠금 안에서 읽는다.
2. 본인 세션·정박 항구·보유량·보급 여유·시장 revision·서버 보정 시각을 확인한다. 견적과 일치할 때 새 거래 ID와 다음 `tradeSequence`를 만든다.
3. 본인 개인 저장과 그 거래의 항구·상품 시장 상태를 한 번의 다중 경로 원자 갱신으로 제출한다. 제출에는 개인 revision, 시장 revision, 거래 ID, 승인 총액과 서버 타임스탬프를 포함한다.
4. 서버 규칙이 두 revision의 정확한 증가, 본인 세션, 거래 순번과 양쪽의 거래 ID 일치를 검사한다. 한쪽이라도 맞지 않으면 전체 요청이 실패해야 한다.
5. 성공 확인 후에만 게임의 자금·화물·압력·거래 결과와 기기 저장을 확정하고 대기 기록을 정리한다. 공개 랭킹은 이 개인 저장 확인 후 갱신한다.
6. 동시 거래 충돌은 본인 기록과 해당 상품만 다시 읽어 새 견적을 표시한다. 기존 견적을 조용히 바꾸어 재체결하지 않는다.

RTDB의 공통 부모에 `update`를 보내되 변경 경로만 전송한다. 클라이언트가 세계 전체를 읽는 루트 트랜잭션은 사용하지 않는다. 다른 이용자의 개인 저장 읽기 권한을 넓히지 않고, 규칙이 갱신 후 두 경로의 상태를 비교하도록 설계한다. 원자 갱신은 Firebase 공식 지원 기능이며 본 프로젝트에 맞춘 revision 검사는 에뮬레이터에서 별도로 입증한다. [원자 갱신 문서](https://firebase.google.com/docs/database/web/read-and-write)

### 자동 저장·재접속·중복 방지

거래 저장과 현재 `CaptainAccount.writeSave`를 같은 쓰기 대기열에서 직렬화한다. 자동 저장이 거래 직전의 오래된 상태로 현금을 덮어쓰지 않도록, 잠금 획득 후 최신 상태를 저장한다. 재시도·새 탭 인계에서도 세션과 두 revision을 확인한다.

거래 대기 ID와 순번은 제출 전에 기기에 기록한다. 응답이 사라졌다면 서버의 마지막 거래 ID와 순번을 조회한다. 이미 처리된 ID는 저장된 결과를 표시하며 다시 체결하지 않는다. 서버 순번이 더 진행됐거나 다른 기기 거래가 확인되면 최신 서버 기록을 열고 오래된 의도를 자동 재제출하지 않는다. 같은 순번·ID가 재사용되어 돈·화물이 두 번 바뀌는 요청은 거부한다.

SDK의 로컬 예상 이벤트를 서버 확정으로 취급하지 않는다. 네트워크 복구 뒤 지연 전송이 승인될 수 있으므로 거래 대기 중 중복 제출·로그아웃 완료·다른 경제 행동을 잠그고 결과를 먼저 확인한다.

## 8. 권한과 검증의 경계

Google 인증·본인 개인 저장 권한·항구/상품 허용 ID·정수 수량·자금 범위·압력 범위·시각과 revision·거래 순번을 서버 규칙으로 검증한다. 시장만 단독 변경하거나 다른 선장의 기록과 짝지은 갱신을 거부한다. 시각 보정에는 `.info/serverTimeOffset`, 최종 시각 검사에는 규칙의 `now`를 사용한다. [서버 시각 문서](https://firebase.google.com/docs/database/web/offline-capabilities), [규칙 조건 문서](https://firebase.google.com/docs/database/security/rules-conditions)

현재 개인 진행이 JSON 문자열이므로 규칙이 그 안의 실제 화물·자금을 직접 파싱하여 검증할 수는 없다. 이번 추천안은 현재 소규모 친구 게임의 클라이언트 계산 신뢰 수준을 이어가며, 합법적인 클라이언트의 동시 거래·중복 지급·중간 실패를 보호한다. 금액의 완전한 서버 권위 검증까지 보장한다고 표현하지 않는다. 그 수준을 도입할 경우 구조화한 경제 저장이나 권한 있는 서버 계산에 대한 별도 계획이 필요하다.

## 9. 비용을 줄이는 운영 방식

기존 RTDB와 정적 배포를 사용한다. 가격 회복은 마지막 거래 시각과 현재 시각의 차이로 계산하므로 매초 회복 값을 서버에 쓰는 예약 작업을 만들지 않는다.

- 교역소를 열 때 선택 항구의 상품 경로만 구독하고 닫거나 항구가 바뀌면 해제한다.
- 항구 비교는 선택한 항구·상품만 제한 조회하고 화면이 열려 있는 동안 재사용한다.
- 추가 입력·매 프레임·지도 이동 때 전체 시장을 다시 내려받지 않는다.
- 회복 시계 갱신은 기기에서 계산하고 DB 쓰기는 실제 거래 확정 때 한다.
- 시장 충돌 재조회는 해당 상품과 본인 기록으로 제한한다. 공개 요약은 기존 변경분 갱신을 사용한다.

실제 거래가 늘면 시장의 읽기·쓰기와 본인 저장 다운로드가 증가한다. 이번 계획은 사용량 실측과 0원 운영을 보장한 결과가 아니다. 구현 시 전송 경로와 크기를 확인하고 의미 있는 증가 요인을 안내한다. 이번 추천안에는 새 유료 서비스 가입이나 요금제 변경을 포함하지 않는다.

## 10. 저장 이관과 배포

- 기존 돈·화물 원가·선박·선단·뗏목 전환 보상 표식·항해·탐험·수집 기록을 이관 전후 비교한다.
- 저장 봉투는 v5로 확장하고 `tradeSequence`의 초기값을 0으로 정한다. 게임 데이터 v3의 호환 읽기를 유지한다. 이전 기기 대기 기록은 현재의 백업·충돌 해결 절차로 보존한다.
- 시장 초기 압력은 0이다. 과거 거래를 소급하여 누적하지 않는다. 기준 시계만 공통 현실 시간으로 바꾸므로 배포 시 기존 개인 시세와 가격 차이가 발생할 수 있음을 업데이트에 알린다.
- 규칙·클라이언트·시장 버전의 전환 단계를 함께 준비한다. 구버전의 개인 저장만 바꾸는 거래가 신규 공동 시장을 우회하지 못하게 v5 진입 조건을 적용하고 새로고침을 안내한다.
- 구현과 검증 뒤 기존 Firebase database 규칙과 GitHub Pages에 배포한다. 공개 파일과 새 버전 식별자를 확인한다.
- 복구가 필요하면 v5와 거래 순번을 읽을 수 있는 수정 버전을 배포한다. 과거 코드나 서버 백업으로 전체 진행을 조용히 되돌리지 않는다.

## 11. 개발 순서

1. **가격 핵심 계산**을 순수 함수로 분리한다. 현실 시각·지역 기준가·압력 회복·상자별 견적·최대 구매를 구현한다.
2. **동시 저장 검증 시제품**을 격리 에뮬레이터에서 만든다. 원자 갱신·두 revision·세션·거래 순번·자동 저장 충돌을 먼저 입증한다. 이 단계를 통과한 저장 구조를 기준으로 화면을 연결한다.
3. **시장 연결 모듈**에 서버 시각 보정·상품별 제한 구독·견적·거래 제출·결과 조회를 묶고 계정 쓰기 대기열과 연결한다.
4. **거래 화면**에 변동률·회복 시간·총액/평균 단가·가격 변경 재확인·대기 상태를 적용한다. 항구 비교·관측 카드·의뢰·이익 계산의 호출부를 정리한다.
5. **저장 이관과 구버전 보호**를 구현하고 기존 저장·뗏목 보상 표식·랭킹을 검증한다.
6. **초반 교역과 사용자 조작**을 검증한 후 패치 노트·안내 JPG의 시세 설명을 갱신하고 기존 주소에 배포한다.

## 12. 검증 기준

| 검증 | 통과 기준 |
| --- | --- |
| 반복 매매 | 같은 항구/상품에서 구매는 압력 상승, 판매는 하락 |
| 원상 회복 | ±10%는 6분 40초, ±30%는 20분 뒤 0. 0을 넘어 반대 방향으로 이동하지 않음 |
| 분할 매매 | 동일 시각·동일 순서에서 대량과 분할 거래의 총액/최종 압력 일치 |
| 가격 한도 | 연속 거래·큰 수량·반대 거래에서도 ±30% 준수 |
| 공통 시간 | 게임 날짜·속도·기기 시간대가 달라도 같은 서버 시각의 동일 입력은 같은 견적 |
| 기기 시계 변경 | 연결 중 시계 변경이 회복·견적을 앞당기지 못하고 재연결 시 다시 보정 |
| 다른 상품·항구 | A항구 와인의 거래가 B항구 와인이나 A항구 소금의 압력을 바꾸지 않음 |
| 여러 선장 | 같은 상품의 같은 revision으로 동시 거래 시 하나만 먼저 체결되고 다른 요청은 재견적 |
| 일부 실패 | 시장과 개인 저장 중 하나만 반영되는 결과가 발생하지 않음 |
| 응답 유실 | 서버 확정 직후 연결을 끊어도 재접속 시 정확히 한 번의 현금/화물 변화 |
| 자동 저장 | 거래 직전 자동 저장·거래·로그아웃이 겹쳐도 확정 잔액/화물이 일치 |
| 권한 | 미인증·타인 저장·단독 시장 변경·역행 revision·재사용 거래 순번 거부 |
| 기존 기록 | 화물 원가·부분 판매·이익·탐험·선단·전환 보상 표식 일치 |
| 화면 | PC와 모바일에서 총액·거래 뒤 예상 가격·확인/대기 상태가 읽히고 짧은 알림의 높이가 내용에 맞음 |
| 비용 경로 | 전체 시장·전체 이용자 저장을 읽는 동작과 주기적 회복 쓰기가 없음 |

공통 기준 시세의 24시간 전체에 걸쳐 시장 압력 0의 리스본↔포르투 첫 와인/건어물 교역을 확인한다. 저가 상품의 정수 반올림 때문에 첫 교역이 항상 손해가 되거나 첫 성장 목표가 막히면, 해당 두 항구의 공급·수입 계수를 최소 범위에서 조정해 조정표를 남긴다. 수요가 이미 포화된 시점에는 다른 상품·항구 선택의 의미를 유지한다. 수치 검증 후 장기 선단 교역에서도 상·하한과 수익 변화를 확인한다.

게임 규칙은 관련 `npm test`, 생성 자료는 `npm run notes:check`, 권한·원자 저장은 `npm run test:rules`에 새 검증을 추가한다. 실제 Firebase SDK의 조회·순회와 네트워크 실패도 에뮬레이터에서 확인한다. 브라우저 사용이 가능하면 실제 화면과 핵심 거래 조작을 확인하고, 도구 제한이 있으면 확인 범위를 구분해 전달한다.

## 13. 계획 단계의 완료 기준

이번 요청은 상세 계획 작성까지다. 수치·공동 시장·저장·비용·검증·작업 순서를 본 문서에 정리했다. 새 게임 규칙 구현, 운영 시장 생성, 규칙 배포, 게임 배포는 업데이트 실행 지시에서 진행한다.
