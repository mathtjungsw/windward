# 바람의 항로 상세 개발계획 · 항해 편의·지역 무역·오프라인 해상 전투

작성일: 2026-11-10, 한국 시간. 상태: **구현·검증 완료 · 배포 진행 중**.

사용자의 ‘개선안을 상세계획으로 작성해줘’ 요청에 따라 현재 백로그를 구체화했다. 이후 사용자의 구현·배포 지시에 따라 실행했다. 아래 본문은 승인 당시 설계를 보존하며 최종 구현 차이와 검증 결과는 실행 기록을 우선한다. 이미 배포된 14종 랭킹·제안 게시판·소유 항구 목록·지도 포격은 유지하고 새 요구와 연결한다.

## 1. 범위와 확정 사항

| 묶음 | 사용자 요청/확정 | 이번 계획의 구현 방향 |

해적 수·새 상품 수·가격 배율·지도 파일 예산·오프라인 교전의 시간 종료 방식은 아래 **추천 기본안**이다. 오프라인 자동 반격은 이번 질문에 사용자가 직접 선택한 확정 사항이다.

### 1.1 유지하는 기존 규칙

- Google 로그인과 현실서버 하나, 현재 선박 성장·기함/동행선·최저 선박 성능 기준을 유지한다.
- 메인 해도는 확대·축소 없는 평면 지도다. 미니맵은 지구본/평면 선택을 유지한다.
- 일반 위치 최소 2초, 정지/접속 유지 30초, 합의 결투 위치 변경 최대 0.25초와 결과 즉시 반영을 유지한다.
- 항구 정보 80해리, 현재 시야 180해리, 발견 흔적 100해리·조사 60해리, 주점 소문을 유지한다.
- 거래 한 건의 판매 전량은 시작 단가로 판다. 상자 수는 다음 시세에 반영하며 시세 회복은 현실 절대시간을 따른다.
- 일반 항구는 실제 누적 투자 지분 **50% 초과** 소유다. 정확히 절반은 무소유다. 리스본·포르투 중립과 기본 세율 0%를 유지한다.
- 해적은 선제공격하지 않는다. 자유 공격은 기본 대포 성능, 합의 결투만 임시 강화한다.
- 패전은 기존 제한 손실과 수리·구조를 유지한다. 돈이 없어도 구조하며 미방문 항구로 보내거나 구조 중 발견·안개 점수를 주지 않는다.

## 2. 현재 코드에서 확인한 출발점

- 원본은 `dist/`, GitHub Pages는 `.github/workflows/pages.yml`에서 이 폴더만 공개한다. Firebase 프로젝트는 기존 `windward-voyage`다.
- 공개 주요 항구 78곳, 호환 항구 112개 ID와 개발 후보 12개 ID가 있다. 이번 계획은 항구 수를 다시 늘리는 작업이 아니다.
- 상품 사전은 총 28종: 일반 23종 + 구버전 혼합 향신료 1종 + 한정 상품 4종이다. 원본은 `tools/port-catalog.json`, `tools/world-catalog.json`, `tools/coastal-sites.json`, 한정품은 `dist/market-catalog.js`다.
- `market-rules.js`는 생산/지역/수입 역할이 있으면 수요 분기를 거치지 않는다. 따라서 취급 상품에 등록한 수입품은 수요 효과를 함께 받지 못하는 경우가 있다. 카카오의 유럽 수요 배치도 전체 점검 대상이다.
- `combat-core.js`의 해적은 6개 고정 지점이다. `save-game.js`의 NPC 진행 검증에도 기존 6개 ID가 직접 들어 있다.
- 토벌 뒤 `npcBattle`은 없어지지만 `selectedNPC`가 남아 HP 0/재출현 대기를 계속 그리는 경로가 있다.
- `selectPort()`는 직접 조종이면 항로를 만들지 않는다. `planDestination()`은 진행 중 항해가 있으면 바로 반환하므로 해상 항로 변경 처리를 함께 정리해야 한다.
- 현재 배 위치는 접속 종료 때 삭제되고, 위치 표시 90초·전투 접속 45초 제한이 있다. 이 숫자만 없애서는 오프라인 선박·안전한 정산이 완성되지 않는다.
- 현재 비공개 게임 저장은 JSON 문자열인 게임 v4/봉투 v5다. 공격자가 그 문자열을 읽거나 피해자의 저장을 덮어쓰도록 바꾸지 않는다.

## 3. 모바일 직접 조종 안정화

### 3.1 입력 처리

1. 방향 패드와 반복 조작 버튼, 그 안의 아이콘/글자에 `user-select:none`, `-webkit-user-select:none`, `-webkit-touch-callout:none`을 적용한다.
2. 방향 패드에만 `touch-action:none`을 적용하고 해당 영역의 문맥 메뉴·기본 선택을 막는다. 페이지 전체의 스크롤·복사·붙여넣기는 막지 않는다.
3. 기존 `preventDefault`, 포인터 캡처, `pointercancel`/`lostpointercapture` 입력 해제를 유지·보강한다.
4. 방향별 단순 불리언 대신 `pointerId → 방향`을 관리한다. 같은 방향을 두 손가락이 누르거나 한 손가락만 취소되어도 나머지 입력이 정확히 남아야 한다.
5. 손 떼기·화면 숨김·앱 전환·화면 회전·모드 변경 때 오래된 입력을 해제한다. 이미 해제된 터치의 비동기 준비 응답이 배를 다시 움직이지 않게 한다.
6. 조작 중 선택이 생겼다면 조작부 안에서 시작된 선택만 해제한다. 채팅/제안/이름/수량 입력의 선택은 유지한다.

글자 선택에 따른 끊김과 실제 렌더링 프레임 저하는 구분해 검사한다. CSS 추가만으로 모든 렉이 해결됐다고 보고하지 않는다.

### 3.2 완료 기준

Android Chrome·iPhone Safari에서 20초 이상 누르기, 빠른 연타, 패드 밖으로 드래그, 두 손가락, 취소 후 재조작을 검사한다. 지도 드래그·PC WASD/방향키·입력창 복사를 함께 확인한다. 실제 기기/브라우저 확인을 못 했으면 DOM 검사와 구분해 기록한다.

## 4. 직접 조종에서 항구 자동 항해로 전환

### 4.1 사용자 흐름

**직접 조종 중 알려진 항구 선택 → 직접 입력 해제 → 자동 항해 모드 → 현재 위치에서 항로 계산 → 가능하면 바로 출항/이동.** 모드 전환과 출항 버튼을 다시 누르지 않는다.

- 지도 항구 표식과 항구 찾기의 이동용 선택에 적용한다. 현재 자동 항해 중 다른 목적지를 명시적으로 선택하면 이동한 거리/소모 보급을 보존하고 현재 위치에서 다시 계산한다.
- 소유 항구 목록의 ‘지도에서 보기’, 미니맵 클릭, 상품 설명 열기는 카메라/정보 보기다. 이 동작으로 출항하지 않는다. 내부 선택에 `navigate`와 `inspect` 의도를 분리한다.
- 현재 정박한 항구를 다시 선택하면 정보만 연다. 미개방 항구를 새로 해금하거나 자동 목적지로 만들지 않는다.

### 4.2 전환 순서와 예외

1. 새 이동 의도 번호를 만들고 키/터치·수동 목표·이전 준비 작업을 정리한다. 누르고 있던 WASD의 자동 반복은 키를 뗄 때까지 다시 받지 않는다.
2. 이동 가능한 계정/서버 상태와 전투·구조·보급·선단 외해 한도를 검사한다.
3. 현재 좌표/남은 보급을 기준으로 새 항로를 만든다. 기존 항로의 시작점으로 되감거나 전 세계를 직선으로 가로지르지 않는다.
4. 필요한 전투 보관금 준비는 기존 원자 큐에서 한 번 처리한다. 기다리는 동안 다른 항구를 고르면 마지막 선택만 유효하다.
5. 성공하면 자동 모드/목적지/예상 소모를 표시하고 이동한다. 모바일 교역창을 다시 자동으로 열어 지도를 가리지 않는다.
6. 항로·보급·전투 조건이 실패하면 현 위치에서 멈추고 구체적 이유를 표시한다. 실패한 이동을 확정하거나 과거 수동 키 입력을 되살리지 않는다.

자동 항해를 멈추거나 직접 조종 버튼으로 돌아가는 기존 조작을 유지한다.

## 5. 해적 UI 정리·수 확대·위치 탭 제거

### 5.1 침몰 후 상태 정리

- 토벌 원자 저장이 확인되면 해당 표적 선택, HP 표식(전투용 내 배 HP 포함), 대포 조작부를 즉시 해제한다.
- 마지막 포탄/명중 효과는 최대 약 1.6초 안에 마무리하고, 토벌 명성은 짧은 알림으로 남긴다. HP 0 창을 30분 동안 남기지 않는다.
- 지연 타이머에는 표적/전투 ID를 붙여 다음 전투의 UI를 지우지 못하게 한다.
- 재접속 때 HP가 남은 실제 `npcBattle`만 복원한다. 재출현 기록만 있는 토벌 완료 해적은 UI를 다시 열지 않는다.
- PvP의 아직 받지 않은 정산 버튼은 NPC 토벌 UI와 구분해 보존한다.

### 5.2 해적 6 → 24척 추천

기존 6개 ID와 진행 기록을 보존하고 고정 지점 18개를 추가하는 첫 목표다. 좌표는 실제 항해 수역·같은 바닷길 검사 후 확정한다. 이동 AI·랜덤 위치 변경·전체 위치 동기화는 추가하지 않는다.

| 해역 묶음 | 합계 | 추천 강도 구성(정찰/중형/기함) | 배치 방향 |
| --- | ---: | --- | --- |
| 유럽·북동 대서양/지중해 | 4 | 3 / 1 / 0 | 초반 연안과 외해의 첫 조우 |
| 카리브·중남미 대서양 | 4 | 2 / 2 / 0 | 섬 사이와 대서양 교역 항로 |
| 아프리카 연안·희망봉 | 4 | 2 / 2 / 0 | 서부/동부 연안과 남단 우회 |
| 아라비아해·인도양 | 4 | 1 / 2 / 1 | 중거리 교역과 외해 기함 |
| 동아시아·동남아시아 | 4 | 1 / 2 / 1 | 해협 바깥·도서 항로 |
| 태평양·오세아니아 | 4 | 0 / 1 / 3 | 섬 간 원양 항로 |
| 합계 | **24** | **9 / 10 / 5** | 기존 6척 포함 |

- 기존 HP 100/240/500, 토벌 명성 50/150/400, 개인별 현실 30분 재출현을 유지한다.
- 기본 배치 목표는 항구 입항 범위 바깥, 부두에서 약 60해리 이상과 연속 수로 확보다. 지도 단순화로 이 수치가 부적절한 지점은 실제 경로로 조정한다.
- 해적 간 권장 거리는 실제 항해 250해리 이상이다. 지형·지역 밀도를 검증하며 숫자를 기계적으로 맞추느라 지나치게 어려운 위치로 보내지 않는다.
- 같은 해적을 재접속/새 탭으로 반복 토벌하지 못하게 하고 기존 처치 랭킹을 초기화하지 않는다.
- 해적 ID 목록을 카탈로그로 분리해 표시·전투·저장 검증·테스트에서 함께 사용한다. 신규 ID가 저장 파서에 거절되는 일을 막는다.

### 5.3 지도에서 발견하고 전투하기

- 상단 ‘전투·해적’ 탭과 모바일 더보기의 전체 해적 위치 목록·거리·‘해역 보기’를 제거한다.
- 기존 180해리 시야 안 해적을 지도에서 선택하면 지도 아래 대포 조작이 열린다. 시야 밖 해적의 위치를 별도 전체 목록으로 알려주지 않는다.
- 다른 선장 배 선택에는 ‘기본 공격/결투 요청’을 연결한다. 결투 수락은 알림으로, 진행 중 전투는 지도 조작부로 복원한다.
- 전리품 수령은 정박 항구의 화물/항구 서비스에서 제공한다. 기존 최대 50상자 보관과 실제 적재 여유 검사는 유지한다.

## 6. 한정 상품 재고와 항구 비용

### 6.1 공유 재고 상한 30상자

- 한정 4종의 생산 항구별 공유 상한을 30으로 통일한다. 회복은 기존대로 현실 2시간에 1상자다. 선박 적재 한도나 계정별 소유 상한을 30으로 바꾸는 것이 아니다.
- 신규 시장 기록은 30상자로 시작한다. 기존 기록은 재고·시각을 유지해 전환 시점까지 구규칙(상한 10)으로 회복분을 계산한 뒤, 그 시점부터 상한 30을 적용한다.
- 구재고가 10으로 가득 찼던 동안의 과거 시간을 새 상한에 소급해 한 번에 30으로 채우지 않는다. 미완료 2시간 회복 구간은 가득 차 있지 않았던 기록에만 이어 적용한다.
- `stockAt`, 거래 견적/확정, 표시 문구, 규칙 검증의 숫자를 공통 설정으로 모은다. 2명이 마지막 재고를 동시에 구매하면 한 요청만 확정되고 실패한 쪽은 돈/화물 변화가 없어야 한다.
- 같은 항구에 판매한다고 공유 한정 재고를 되채우는 새 규칙은 추가하지 않는다.

## 7. 지역 특색을 살린 전체 교역 개편

### 7.1 전체 점검 범위와 원본

78개 현재 항구·개발 후보 12곳의 생산/공급/중계/수요를 점검한다. 퇴역 항구와 구버전 화물도 판매 호환성을 유지한다. 생성된 `dist/port-economy.js`, `world-catalog.js`, `coastal-sites.js`를 직접 고치는 대신 JSON 원본과 생성기를 수정한다. 상품 개수를 24로 고정한 생성 검사도 새 명세에 맞춘다.

항구별 추천 구성은 구매 가능 일반품 3~6종, 대표 특산 1~2종, 두드러진 수입 수요 2~4종이다. 이웃 항구에 일부 공통품을 두되 특산/수요 조합을 달리한다. 정보가 없는 모든 항구에 모든 상품을 판매 목록으로 풀지 않는다.

### 7.2 가격 계산안

공급 역할과 수입 수요를 **서로 배제하는 분기에서 독립된 보정으로** 바꾼다. 아래 값은 최초 조정용 추천값이다.

| 공급 역할 | 기준 배율 | 수요 단계 | 수요 배율 |
| --- | ---: | --- | ---: |
| 주요 생산 | 0.70 | 일반 | 1.00 |
| 지역 공급 | 0.90 | 높은 수요 | 1.30 |
| 수입·중계 | 1.15 | 희소 수입 수요 | 1.80 |
| 비취급·뚜렷한 수요 없음 | 판매 평가 0.80, 구매 불가 | — | — |

```text
지역 기준가 = 상품 기본가 × 공급 배율 × 수요 배율
거래 기준가 = 지역 기준가 × 기존 현실 날짜 변동
구매 = 각 상자별 가격 압력 반영 + 거래세
판매 = 거래 시작 압력을 반영한 단가 × 전량 − 거래세
실현 이익 = 판매 수령액 − 판매분 매입 원가
항로 비교용 순이익 = 왕복 실현 이익 − 실제 보급 비용
```

- 동일 항구의 매입/판매는 같은 지역 기준가와 기존 판매 할인 0.88을 공유한다. 판매 수요만 올리고 구매 기준은 낮게 남겨 즉시 차익이 생기지 않도록 한다.
- 생산 항구가 같은 상품의 ‘희소 수입 수요’로 동시에 지정되는 모순은 자료 검사에서 거절한다. 취급 목록이 없는 수요 항구도 수입 수요를 적용해 보유 화물을 판매할 수 있다.
- 기존 가격 압력 ±30%, 상자당 변화·현실 시간 회복·하루 변동은 먼저 유지하고 새 지역 가격차와 함께 검증한다. 거래세·한정품 재고와 상호작용을 점검한 뒤 필요한 수치 조정은 명시한다.
- 한정품은 생산지 기준을 유지하고 지정 소비항/적합한 수입 지역을 일반 재판매처와 구분한다. 소비항 기준 배율 2.0~2.4, 기타 적합 수요항 1.4~1.8을 추천하며 왕복 검증 후 맞춘다. ‘어느 항구나 무조건 최고가’가 되지 않게 한다.

파동·압력·세금이 없는 **설계 산술 예시**: 일반 카카오 기본가 88, 생산 0.70이면 매입 62 D, 수입 1.15×희소 수요 1.80이면 판매 160 D다. 일반 도자기 기본가 120은 같은 예에서 84 → 218 D다. 이는 구현 전 계산 예시이며 실제 게임에 적용된 견적이나 항해비 차감 후 보장 이익이 아니다.

- 전체 항구/상품의 매입·판매표와 대표 항로 결과를 정적 검수 보고서로 남긴다. 게임 이용자에게 모든 항구의 미발견 시세를 실시간 공개하는 기능을 새로 넣는 것은 아니다.
- 새 상품 거래는 기존 종류 랭킹에 고유 ID로 반영한다. 최고 한 거래/누적 이익은 기존 기준을 유지한다.

## 8. 오프라인 선박과 자동 방어

이번 계획에서 가장 중요한 저장 변경이다. 표시용 접속 TTL만 없애는 방식으로 구현하지 않는다.

### 8.1 사용자에게 보이는 동작

- 접속을 종료해도 마지막 서버 확인 위치에 정지한 배가 남는다. 자동 항해를 오프라인 시간만큼 계속 진행시키지 않는다.
- 다른 선장의 180해리 시야 안에서만 표시하고 ‘오프라인’ 표식을 붙인다. 전체 접속 인원에는 더하지 않는다. 한 계정은 지도에 한 선단만 나온다.
- **실제 정박한 모든 일반/대형/개발 항구는 공격 금지**다. 항구 소유·세율과 무관하며 항구 가까운 바다에 멈춘 것은 정박이 아니다.
- 해상에서 공격받으면 장착된 대포가 원래 품질·명중률·피해·재장전으로 자동 반격한다. 장착 대포가 없으면 포격 반격은 없다. 먼저 다른 배를 찾아 공격하지 않는다.
- 재접속하면 오프라인 전투 결과를 먼저 반영하고 항해를 재개한다. 오프라인 동안의 명성/격파는 실제 결과로 집계한다.
- 해상 로그아웃 메뉴와 업데이트 안내에 ‘접속을 종료해도 해상에서는 공격받을 수 있어요. 항구 정박 중에는 보호돼요’를 표시한다. 단순 접속 수가 늘어난 것처럼 보이지 않게 실제 접속/오프라인 배 수를 구분한다.

### 8.2 데이터 분리안

아래 경로명은 구현 설계명이다. 기존 이름과 책임이 겹치는 부분은 통합해 중복 장부를 줄인다.

| 경로/역할 | 내용과 접근 | 갱신 시점 |

접속 여부는 기존 가벼운 roster/연결 경로로 판정한다. 영구 선박에는 90초 TTL을 적용하지 않고, 오프라인 배를 살려 두기 위해 heartbeat를 보내지 않는다. 기존 위치 경로와 새 경로는 이관 기간에 중복 표시하지 않고 uid로 합친다.

### 8.3 마지막 위치와 저장의 일치

- 눈에 보이는 위치는 2초마다 바뀌는데 본인 저장이 15~20초 전이라고 해서, 공격 위치와 재접속 위치가 크게 달라져서는 안 된다.
- 위치와 같은 순번의 작은 **본인 전용 이동 체크포인트**를 함께 저장한다. 장거리 항로 전체·전체 탐험 지도·화물 JSON을 2초마다 반복 보내지 않는다. 항로는 경로 ID로 참조하고 미저장 탐험 변화는 제한된 증분으로 둔다.
- 입항·상품/선박 변경·새 발견 같은 중요한 행동은 본인 저장과 선박 요약의 기준 revision을 일치시킨다. 현재의 전체 저장 주기를 전부 2초로 줄이는 방식은 피한다.
- 정상 로그아웃은 저장 완료 뒤 선박 상태를 고정한다. 비정상 종료는 마지막 확인한 순번까지만 남긴다. 미전송 기기 기록은 기존처럼 보존해 충돌을 안내하되 서버에서 확정된 전투 피해를 덮어쓰지 못하게 한다.

### 8.4 전투 시작·자동 반격·종료

1. 공격자는 현재 해역에서 찾은 배를 선택한다. 서버 기준 오프라인 상태/epoch, 실제 해상 위치, 정박/구조/패전 보호, 장착 대포와 보관금을 다시 확인한다.
2. 양쪽 선단 슬롯과 대상 revision을 같은 요청으로 잠근다. 같은 배에 동시에 시작한 전투는 하나만 성립한다. 오프라인 표적이라는 이유로 소유 세션이나 비공개 저장 쓰기 권한을 넘기지 않는다.
3. 첫 유효 포격과 준비된 첫 자동 반격을 같은 전투 진행으로 확정한다. 공격자가 첫 발사 직후 창을 닫아 항상 무반격 이득을 얻는 경로를 줄인다.
4. 이후 공격자 화면이 유효한 교전을 진행하는 동안, 준비된 방어 대포를 현실 재장전 간격에 맞춰 처리한다. 방어 순서·대포 ID·발사 시각·명중/피해·방 순번을 기록한다. 장식 애니메이션은 서버 확인 뒤 재생한다.
5. 자동 반격 요청은 `autoDefense` 같은 별도 행동으로 제한한다. 인증된 공격자가 현재 방의 잠긴 방어 대포로 정해진 반격만 진행할 수 있게 검증하며, 다른 대상/추가 대포/임의 수치·미래/과거 발사는 거절한다. 현재 확률 방식과 규칙의 신뢰 한계도 함께 시험한다.
6. 브라우저 중단 뒤 재개할 때 미뤄진 수백 발을 한꺼번에 계산하지 않는다. 현재 유효 시간 안의 다음 행동만 처리하고 이미 끝난 방을 재생하지 않는다. 양쪽이 아무것도 하지 않는 동안 상시 서버 AI를 돌리지 않는다.
7. 방어 선장이 접속하면 자동 방어/수동 방어를 epoch로 인계한다. 한 대포가 양쪽에서 동시에 발사되지 않도록 하고, 전투 중에는 먼저 방을 복원한 뒤 조종을 허용한다.

**오프라인 교전 종료 추천:** HP 0이면 기존 패전 정산, 공격자의 명시적 항복/후퇴는 기존 패전 처리다. 180초 시간 종료·공격자 이탈만으로 오프라인 표적을 자동 패배시키지 않고, 미격파 교전은 무승부 종료하며 실제 HP 손상/재장전은 유지하고 추가 약탈·격파를 주지 않는 안을 추천한다. 오프라인 45초 경과만으로 승리시키는 기존 접속 종료 분기는 이 모드에서 사용하지 않는다. 이는 사용자에게 확정받은 별도 승패 변경이 아니라 오프라인 전투의 무공격 약탈을 막기 위한 추천 세부 규칙이다. 합의 결투의 기존 시간 판정과 구분한다.

### 8.5 오프라인 결과와 자산 보존

- 현재처럼 출항 때 보관한 돈 최대 2,000 D·화물 최대 5상자 한도만 약탈 대상으로 사용한다. 다른 선장이 보유금/전체 화물을 읽어 새로 빼 가게 하지 않는다.
- 각 전투의 정산 ID/순번을 한 번만 인정한다. 오프라인 승자의 원래 보관 원금을 전투 때마다 반복 지급하지 않는다. 유지 중인 원금·새 획득분·원금 반환 여부를 분리해 여러 교전 후에도 보존식을 검사한다.
- 선박 HP는 공유 전투 상태를 기준으로 이어지고, 과거 개인 저장 HP로 회복시키지 않는다. 수리/개량·장착 변경은 정박 서비스 원자 영수증과만 결합한다.
- 패전한 오프라인 배는 즉시 `rescuePending`으로 공격 불가·해상 목록 제외 처리한다. 방문 목록을 타인에게 공개하거나 미방문 항구로 임의 이동시키지 않는다. 재접속한 본인의 저장으로 가까운 실제 방문 항구를 계산해 기존 구조를 마무리한다.
- 수리·구조 비용과 제한 화물 손실은 본인 복원 때 미수령 정산 순번으로 한 번 반영한다. 명성·돈을 음수로 만들거나 무자금 귀환을 막지 않는다.
- 피해자 로그인을 처리할 때 미적용 결과를 읽기 → 이동 체크포인트 복원 → 결과 적용/필요한 구조 → 본인 저장과 수령 순번 원자 확인 → 플레이 시작 순서로 한다.
- 중간 통신 단절이면 ‘결과 확인 중’으로 두고 추가 자산 변경을 막는다. 서버 영수증 확인 뒤 같은 결과를 한 번만 반영한다.

보존 검사에서는 양쪽의 개인 보유금+보관 원금+미수령 획득금을 합해 전투 전 금액에서 확정된 수리/구조 비용만 빠졌는지 확인한다. 양쪽 화물+보관 화물+미수령 전리품의 품목별 수량/원가도 합산한다. 원금을 반환했다는 이유로 승리 때마다 총액이 늘거나 같은 손실을 다시 빼는 경우는 실패다. HP 회복은 정박 수리·기존 패전 구조 같은 정해진 사건에서만 발생해야 한다.

### 8.6 필수 서버 검증

기존 root 다중 경로 원자 요청·revision 비교를 확장한다. `fleetStates`의 전투 자산 revision과 `privateSaves`의 확인 순번을 연결해 오래된 자동 저장/클라이언트가 피해를 지우지 못하게 한다. 이동 revision과 자산 revision은 분리해 매 2초 위치 변경 때문에 전체 게임 저장이 충돌하지 않게 한다.

정박과 공격의 경합은 같은 선박 자산 revision을 사용해 하나만 먼저 성립하게 한다. 공격이 이미 성립한 뒤 단순 정박 플래그 덮어쓰기로 탈출하지 못하고, 실제 항구 이탈/패전 구조 규칙으로 정산한다. 반대로 입항이 먼저 확정되면 공격·반격 모두 거절한다.

친구용 브라우저 계산 모델을 유지하지만 제3자의 임의 피해/약탈 쓰기는 허용하지 않는다. 규칙으로 검사 가능한 방 상태·슬롯·대포·쿨다운·대상·자산 보존식을 에뮬레이터에서 검증한다. 구현 전 구조 검증에서 빈틈이 나오면 해당 원자 처리와 규칙을 보완하며, 검증 없이 표시만 먼저 공개하지 않는다. 별도 유료 서버 도입을 자동 결정하지 않는다.

## 9. 지도 사실감과 한국어 지명

### 9.1 표현

- 밝은 바다·육지 톤을 유지한다. 전 세계 대륙 윤곽은 더 정교하게, 항구·해협·작은 섬은 항해에 필요한 수준으로 보강한다.
- 기본은 경량 전 세계 벡터, 항해 중요 지역은 정밀 자료를 선택 가공한다. 산지 음영과 연안/외해 색을 추가하되 해안 거리로 만든 색을 실제 측량 수심이라고 소개하지 않는다.
- [Natural Earth 사용 조건](https://www.naturalearthdata.com/about/terms-of-use/)은 벡터/래스터 자료를 public domain으로 안내하며, [10m 물리 자료](https://www.naturalearthdata.com/downloads/10m-physical-vectors/)에는 해안·육지·작은 섬·강 등이 있다. 원본을 그대로 전부 내려받게 하지 않고 필요한 도형만 가공한다. 자료 버전·출처·가공 기록을 남긴다.
- main 고정 배율, 두 미니맵, 시야/안개/강 항로·동서와 남북 연결을 유지한다. 위성사진 스트리밍·유료 지도 API·3D 주 화면은 이번 기본안에 없다.
- 지도 변경으로 배가 육지 위에 보이면 저장을 초기화하지 않는다. 신규 육지와 기존 부두/실제 항로를 먼저 조정하고 불가피한 좌표 보정은 원본 백업과 동일 수로 내 보존 원칙으로 처리한다.

### 9.2 지명

한국어 주요 지명 **약 60개**를 첫 추천 목표로 한다. 실제 목록/좌표는 정적 명세에서 검증한다.

| 종류 | 예시 | 화면 기준 |
| --- | --- | --- |
| 대양·바다 | 대서양·인도양·태평양·지중해·카리브해·아라비아해 | 넓은 수역 중심, 약 13~16px |
| 만·해협 | 기니만·벵골만·말라카해협·대한해협 | 항구 표식과 구분, 좁은 곳은 우선순위 조정 |
| 반도·지역 | 이베리아반도·스칸디나비아반도·아라비아반도·동남아시아 | 육지 영역, 약 12~15px |
| 군도·곶 | 카나리아제도·희망봉 등 | 실제 영역 확인, 항구 글씨와 겹침 회피 |

- 화면 기준 글씨 크기와 은은한 색/얇은 테두리로 읽히게 한다. 지도 좌표 배율 때문에 글자가 지나치게 커지지 않도록 한다.
- 한 화면 기본 표시 목표는 PC 12~16개, 모바일 6~8개다. 표적·항구·항로·HP·조사 행동과 겹치면 지명을 먼저 줄인다. 클릭을 가로채거나 길게 눌러 선택되지 않게 한다.
- 일반 지리는 배경으로 보일 수 있지만 지명 때문에 미발견 항구·발견물 아이콘/위치가 드러나거나 탐험 점수가 늘지 않는다. 안개와 전투 표식은 별도 레이어로 둔다.
- ‘지명 표시’ 켜기/끄기는 기기 설정의 추천 편의 기능이며 기본 켜짐으로 계획한다. 새 계정 저장/서버 동기화를 요구하지 않는다.

### 9.3 성능·비용 목표

현재 관련 5개 지도 자료의 압축 전 합계는 약 1.95 MB다. 새 자료+음영의 원본 총량 **8 MB 이내**를 최초 최적화 목표로 삼되 실제 전송 압축 크기와 최초/재방문 로딩을 별도 측정한다. 원본 공개 사이트의 약 50 MB 자료 묶음을 그대로 게임에 붙이지 않는다.

보이는 영역 위주로 그리기, 정적 지형 캐시, 지도 변경 때만 라벨 배치 갱신을 사용한다. 모바일 균형 품질을 기본으로 무거운 장식 효과를 제한하고 핵심 지형/조작 가독성은 유지한다. 지도와 지명 때문에 Firebase 조회/저장을 추가하지 않는다.

## 10. 기존 저장·자료 이관과 구버전 호환

### 10.1 이관 원칙

- 목표 봉투 v6 / 게임 v5를 추천한다. 실제 필요한 필드와 구버전 차단을 구현하면서 확정하고, 이름만 올리는 이관은 하지 않는다.
- 현재 돈·화물 수량/매입 원가·배별 ID/단계·장착 대포/재장전·보급/크레딧·발견·방문·안개·소문·랭킹·항구 투자/개발을 보존한다. 뗏목 전환 보상이나 과거 보상을 다시 주지 않는다.
- 신규 상품 ID는 추가 방식으로 넣고 구버전 혼합 향신료는 계속 판매하게 한다. 새 해적 ID를 중앙 명세에서 검증하고 기존 토벌 대기 시간을 보존한다.
- 시세 압력·회복 시각과 한정 재고는 버전별 이관 함수로 보존한다. 새 가격 적용은 공개 시점부터이며 보유 화물의 과거 원가를 새 기본가로 바꾸지 않는다.
- 구버전이 30상자 시장을 10상자로 덮거나 새 전투 피해를 지우지 못하게 저장/경제/전투 프로토콜 버전을 검사한다. 구버전에는 새로고침 안내를 주며 기존 기록을 지우지 않는다.

### 10.2 오프라인 선단 최초 등록

기존 오프라인 선장도 마지막 저장을 기반으로 한 번 등록하는 이관을 계획한다. 구현 시 운영 원본을 비공개 백업하고 uid별 최신 저장·진행 중 전투·보관금을 확인한다.

1. 활동 중 세션/교전은 먼저 상태를 구분한다. 서버 버전 경계와 기록 revision을 확인하고, 적용 중에 정상 항해 기록을 과거 값으로 덮지 않는다.
2. 등록 ID와 원본 revision으로 작업 영수증을 남긴다. 이미 가진 전투 보관금은 재사용하고 없으면 기존 보관 규칙으로 분리한다. 보유금+보관금, 화물+보관 화물 총량은 바뀌지 않는다.
3. 본인 저장·이동 체크포인트·선단 상태·보관금이 같은 등록 ID를 확인할 때까지 선박은 공격 가능한 `ready`로 공개하지 않는다. 중간 실패는 같은 등록 ID로 복구하며 중복 공제/배 복제를 하지 않는다.
4. 최종 확인 뒤 영구 해역 목록에 등록한다. 정박 배는 보호 상태로, 해상 배는 마지막 확인 위치로 둔다. 과거 저장의 시각을 현재 접속 시각으로 바꾸지 않는다.
5. REST ETag/원자 규칙의 적용 범위를 실제로 검증한다. 서로 다른 경로의 관리자 쓰기를 단순한 연속 요청이라고 해서 원자 이관이라고 부르지 않는다. 준비→확인→공개 상태와 재실행 가능한 영수증으로 복구성을 확보한다.

이미 접속 중인 계정은 새 버전 복원/인계 시 같은 등록 절차를 밟고, 작업 전후 총 자산·방문·탐험·장비가 일치하는지 검사한다. 이 계획 단계에서 운영 데이터는 읽거나 변경하지 않았다.

## 11. 비용과 통신 설계

- 기존 GitHub Pages/Firebase 구성을 활용한다. 지도·지명·상품/해적 카탈로그는 정적 파일이다. 새 유료 API·Cloud Functions·Blaze 전환을 전제로 하지 않는다.
- 움직이는 선박의 2초 위치 요약과 작은 본인 체크포인트, 실제 공격 시 자동 반격/영수증 때문에 현재보다 저장·전송량은 증가한다. 특히 인근 해역에 영구 배가 누적되면 초기 조회량이 늘 수 있음을 명시한다.
- 해역별 제한 조회·uid 중복 제거·빈 결과 캐시를 사용한다. 기존 구역당 100개 제한을 출발점으로, 가득 찬 구역은 화면의 가까운 하위 해역으로 나누어 오래된 오프라인 배가 영구 누락되지 않게 한다. 단순히 최근 시간순 100개로 자르는 방식은 사용하지 않는다.
- 지도상 최대 29개 다른 선단 표시는 우선 거리 기준으로 고르되 현재 전투 상대는 포함한다. 명부·접속 수와 지도 표시 수를 구분한다. 29척을 넘는 전투 근접 밀집 상황의 표시 정책은 부하 검사에서 확인한다.
- 오프라인 전투를 위해 다른 선장 전체 저장·전체 탐험 지도·전체 시장을 구독하지 않는다. 공격/정산 ID의 현재 미수령 결과와 작은 누적 요약만 유지하고, 수령 확인된 오래된 상세 기록의 정리 기준을 만든다.
- 무료 한도는 무제한이 아니다. 가격과 사용량을 매 작업의 승인 조건으로 만들거나 비용 추정만으로 승인된 개발을 중단하지 않는다. 실제 외부 유료 서비스 도입이 필요해질 경우에만 범위 밖 결정으로 설명한다.
- 참고한 공식 문서: [GitHub Pages 제공 범위](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [RTDB 과금 기준](https://firebase.google.com/docs/database/usage/billing). 이번에는 운영 월 사용량을 새로 측정하지 않았으며 0원 보장을 하지 않는다.

## 14. 향후 업데이트 실행 시 배포·복구 순서

1. 최신 운영 규칙과 이관 대상 저장을 비공개 백업하고 이관을 미리보기로 확인한다. 기존 활성 전투/세션의 처리 경계를 확인한다.
2. 새 규칙·원자 프로토콜·기존 기록 복원을 에뮬레이터에서 통과시킨다. 유료 요금제나 외부 서비스 변경은 자동으로 하지 않는다.
3. 공격 가능 상태를 준비 중으로 유지하며 새 저장/시장 전환·기존 선단 등록을 검증한다. 준비되지 않은 계정을 노출해 공격받게 하지 않는다.
4. 호환 규칙/읽기 경로 → 새 클라이언트/정적 자료 → 등록 확인/새 프로토콜 활성화 순서로 배포한다. 구버전은 명확한 새로고침 안내로 유도한다.
5. 운영 규칙을 로컬 검증본과 비교하고 GitHub Actions 성공·공개 파일 일치를 확인한다. 기록에는 실제 커밋·시각·검사 범위를 남긴다.
6. 실패 시 새 전투 진입을 막고 결과 미확인 기록을 보존해 복구한다. 사용자가 승인하지 않은 전체 DB 삭제/초기화나 과거 백업의 무조건 덮어쓰기를 하지 않는다. 이미 새 버전에서 생긴 거래/피해는 변환해 보존하며 복구한다.

## 17. 구현 중 추가 지시: 내 물품 최고가 판매처

사용자가 개발·배포를 명시적으로 요청해 이번 실행에 포함했다. 화물창/물품별 버튼과 모바일 더보기에서 열고 보유 화물(정산 보관 포함)을 선택한다. 전체 주요 항구 및 교역소 2단계 이상 개발 항구, 또는 알고 있는 항구만 비교한다. 현재 개인 세율·교역 제한을 반영한 예상 수령액 상위 5곳을 보여준다. 검색 시각(한국 시간)과 ‘지금 검색한 시점에 조회한 시세 기준 최고가이며 실제 판매할 때 달라질 수 있다’는 문구를 표시한다.

검색 버튼을 누를 때만 선택 상품의 시장/소유 정보와 필요한 개인 정책을 읽는다. 캐시를 우회한 현재 REST 조회이며 항구 작업은 동시 6개로 제한한다. 창을 닫으면 새 항구 조회를 더 시작하지 않는다. 일부 실패/시간 제한은 누락 항구 수와 함께 표시해 전체 최고가로 단정하지 않는다. 기존 거래 확정 시에는 실제 정박지에서 새 견적을 확인한다. 가격 열람이나 지도 보기는 항구 발견·방문·안개·명성을 만들지 않는다.
