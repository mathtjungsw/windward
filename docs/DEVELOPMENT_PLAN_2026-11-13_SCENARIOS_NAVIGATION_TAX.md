# 바람의 항로 상세 개발계획 · 시나리오·입항·항구 운영

작성일은 2026-11-13이다. 아래 상세계획에 따른 로컬 개발·검증을 완료했다. 적용 내용과 검증 범위, 운영 배포 시 저장 버전 전환은 [개발 기록](LOCAL_DEVELOPMENT_2026-11-13_STORIES_HARBORS_TAX.md)을 따른다. 아래 ‘기존 동작’은 개발 전 조사 기록이고 ‘초안’ 수치는 최초 구현 기준을 보존한 것이다.

## 2. 초보자 과정 · 첫 항로의 선장

### 2.1 이야기와 화면

리스본의 항해 조합이 처음 출항하는 선장에게 작은 교역을 맡긴다. 포르투에서 첫 판매를 마치고 다른 항로를 준비하면서 항해·교역·소문·선단 관리 메뉴를 익힌다. 항구 담당자와 교역 상대의 짧은 대화가 앞 장의 행동을 다음 장의 목표로 이어 준다.

- 6장, 장마다 5개 핵심 단계로 총 30단계를 구성한다. 여러 메뉴를 소개하는 단계는 짧은 하위 안내로 펼친다. 한 화면에 긴 설명을 모두 넣지 않는다.
- 항해자의 의뢰 패널에 현재 장·할 일·진행 수·해당 메뉴 열기를 표시한다. 큰 대화창은 수락·장 마무리에 사용하고 항해 중에는 접을 수 있는 작은 진행 패널을 쓴다.
- 각 장에 도입 대화, 실제 행동, 결과 대화와 다음 목적을 넣는다. 이미 읽은 대화 다시 보기와 장별 진행 저장을 제공한다.
- 출항 전 보급량·빈 적재칸·소지금을 검사하고 부족한 조건과 해결 메뉴를 안내한다. 기본 과정에는 마감·실패 벌금·필수 전투를 두지 않는다.

### 2.2 장별 단계

| 장 | 이야기 | 핵심 단계 5개 |
| --- | --- | --- |
| 1. 리스본의 견습 선장 | 조합에서 첫 화물을 맡길 준비 | 의뢰 수락 → 내 배 보기 → 보유금·적재량 확인 → 목적지와 예상 보급 확인 → 와인 1~3상자 구매 |
| 2. 포르투의 첫 거래 | 북쪽 교역 상대에게 도착 | 포르투 항로 선택 → 자동 출항 → 실제 입항 → 와인 판매 → 보급하고 거래 결과 확인 |
| 3. 돌아오는 장부 | 스스로 두 번째 거래 준비 | 포르투 상품 가격 확인 → 적재 여유 내 1~3상자 구매 → 리스본 귀항 → 판매 → 시세·손익·최고가 판매처 메뉴 확인 |
| 4. 내 손으로 고르는 항로 | 바다와 지도를 다루기 | 직접 조종·정지 연습 → 항구 선택으로 자동 항해 전환 확인 → 항구 즐겨찾기 등록·목록 다시 열기 → 평면/지구본 미니맵 전환 → 항해일지 확인 |
| 5. 주점의 이야기 | 교역 너머의 탐험 소개 | 해당 항구 소문 읽기 → 소문노트 다시 열기 → 숨기기·복원 체험 → 내 발견 도감과 조사 방법 보기 → 근처의 다음 탐험 목표 확인 |
| 6. 나의 다음 항해 | 성장과 다른 선장의 활동 소개 | 조합 의뢰 화면 → 조선소·매각·보관 화면 → 대포·아이템·부선장 화면 → 선장 목록·랭킹·채팅 화면 → 공동 사업·소유 항구·설정·메뉴 찾기 안내 후 졸업 |

직접 조종 연습은 건너뛰기를 제공한다. 유료 행동·선박 구매·매각·대포 발사·실제 채팅 전송은 해당 단계의 필수 완료 조건에서 제외한다. 아직 열리지 않은 기능은 같은 화면의 잠금 이유와 설명을 확인하면 안내 단계를 완료한다. 관련 버튼 자체가 숨겨져 있으면 안내용 기능 소개를 제공한다. 소문을 숨겼다가 다시 표시한 기록도 단계 진행에 반영한다.

최초 와인 구매·첫 입항·판매·보급 같은 핵심 행동은 실제 성공 후 완료한다. 보급이 이미 가득 차 있으면 현재 수량과 보급 화면 확인으로 처리한다. 첫 판매는 이익 여부를 조건으로 요구하지 않는다. 출항을 시도했다가 보급 부족으로 실패한 행동은 출항 성공으로 인정하지 않는다.

### 2.3 보상과 기존 기록

- 신규 초보 과정 장 보상은 각 200 D, 총 1,200 D를 초안으로 한다. 장별 한 번만 지급하고 지급 영수증을 저장한다.
- 기존 4개 의뢰와 미수령 보상 400/650/1,000/1,500 D는 별도 기존 목표로 보존한다. 기존 수령분은 다시 지급하지 않는다. 초보 과정과 기존 의뢰 보상은 화면에서 출처를 명시한다.
- 이미 보존된 실제 입항·거래·소문 읽기 기록으로 증명되는 단계는 인정한다. 이전 저장에 없던 메뉴 열람·직접 조종 여부는 추정하지 않고 간단히 다시 확인하게 한다.
- 신규 뗏목·10일 보급·시작 자금으로 리스본–포르투 왕복을 끝낼 수 있는지 검증한다. 항구 봉쇄·시세 변동·적재 부족 시 다른 소량 상품 또는 동일 권역 기항을 제안한다. 정체를 해결하려고 기록 초기화나 세계일주 능력을 부여하지 않는다.

## 3. 중급·고급 역사 시나리오 공통 규칙

- 중급 각 6장 약 16단계, 고급 각 8장 약 20단계를 목표로 한다. 초보 과정을 포함해 핵심 단계 약 102개와 선택 안내를 구성한다.
- 장마다 등장인물의 요청·이동이나 교역·기록 확인·결말 대화를 연결한다. 같은 항구 방문 횟수만 반복해서 분량을 채우지 않는다.
- 시나리오는 항구 조합의 ‘항해자의 이야기’에서 목록을 보고 수락한다. 주점에서 시작 단서도 듣고 소문노트에서 다시 확인할 수 있다. 현재 진행 이야기는 작은 패널에 하나를 추적하며 다른 이야기로 바꿔 볼 수 있다.
- 중급 해금 초안은 선박 6단계·실제 방문 10항구, 고급은 12단계·실제 방문 20항구·중급 1편 완료다. 실제 항로의 원양 능력과 식량·적재 조건은 해금 수치와 별도로 검사한다. 기존 이용자는 해당 실적을 바로 인정한다.
- 장별 체크포인트를 저장한다. 구조·후퇴·일시 중단 뒤 완료한 장을 다시 요구하지 않는다. 구조 항해·지도 경계 연결로 지정 항로 통과를 대체할 수 없다.
- 스토리 의뢰에는 현실 마감과 명성 벌점을 두지 않는다. 별도로 수락한 일반 조합 의뢰는 기존 마감을 적용한다. 화면에서 두 조건을 설명한다.
- 시나리오 전용 납품은 기존 화물을 쓰는 경우 대상 품목·수량을 표시하고 확인받는다. 조합과 스토리 납품에 같은 화물이 이중으로 사용되지 않게 처리한다.
- 최종 보상은 계정별 최초 완료 한 번만 지급한다. 다시 읽기는 보상을 재지급하지 않는다. 소모 아이템 사용 후에도 완료·획득 이력을 보존한다.
- 시대를 넘나드는 범선·노선 배경으로 구성한다. 증기선 운항 단계는 넣지 않는다. 항구 설명에 역사적 배경과 게임 속 창작 대화·임무를 구분한다.

### 3.1 중급 1 · 킬와의 교역 장부

킬와는 현재 독립 방문 항구가 아니라 발견물 `ruin-kilwa`로 존재한다. 킬와 관련 임무의 접수·보고는 잔지바르에서 하고 실제 유적은 기존 조사 지점을 이용한다. 이번 시나리오를 위해 항구를 임의 추가하지 않는다.

| 장 | 임무와 이야기 진행 |
| --- | --- |
| 1. 잔지바르의 낡은 장부 | 주점의 장부 소문을 읽고 조합에서 요청을 수락한다. 거래 기록과 조사 기록이 필요하다는 단서를 듣는다. |
| 2. 남쪽에서 온 소식 | 잔지바르–마푸투 항로와 보급을 준비하고 마푸투에 실제 입항한다. 현지 교역 담당자의 증언을 얻는다. |
| 3. 흩어진 물품 기록 | 마푸투의 면직물과 잔지바르의 교역품을 소량 거래하고 납품 기록 두 가지를 모은다. 수량은 각 3~5상자 초안이다. |
| 4. 바다 건너온 도자기 | 잔지바르에서 도자기를 확보해 장부의 아시아 교역 흔적과 대조한다. 현재 시장의 구매 가능한 품목만 사용한다. |
| 5. 킬와의 흔적 | 기존 킬와 유적의 흔적에 접근해 조사하고 도감 설명을 읽는다. 이미 조사한 이용자는 도감 재확인으로 대체한다. |
| 6. 장부를 잇는 사람 | 잔지바르에 귀항해 화물·기록을 제출하고 아미나와 합류 대화를 진행한다. |

첫 완료 보상 초안은 4,000 D와 가상 부선장 아미나다. 효과는 동행 시 인도양 지정 항구의 개인 조합 납품 보수 +5%다. 적용 항구 ID는 잔지바르·마푸투·무스카트·고아·아덴·콜롬보로 시작하며, 의뢰 수락 시 보수 계산 조건을 고정해 지급 직전 부선장 교체로 추가 보상을 만들지 않게 한다.

13~16세기 킬와를 통한 인도양 교역과 중국 도자기 거래를 역사 배경으로 삼는다. 장부·아미나·납품 요청은 게임 창작이다. [UNESCO 킬와 유적](https://whc.unesco.org/en/list/144/)

### 3.2 중급 2 · 말라카의 중계상

| 장 | 임무와 이야기 진행 |
| --- | --- |
| 1. 해협의 중개 의뢰 | 말라카에서 창작 상인의 요청을 받고 품목·시세 비교 방법을 확인한다. |
| 2. 서쪽의 교역 상대 | 콜롬보까지 갈 수 있는 배·식량을 준비하고 기항한다. 계피 3~5상자를 확보한다. |
| 3. 다시 말라카로 | 말라카에서 계피를 납품하고 중계 무역 설명을 읽는다. 일반 시장 이익과 의뢰 보수는 구분한다. |
| 4. 동쪽 창고의 표식 | 자카르타에 실제 입항해 구매 가능한 지정 향신료 3~5상자를 확보하고 창고 담당자의 기록을 받는다. |
| 5. 두 장의 장부 | 말라카 귀항과 두 번째 납품을 마친다. 최고가 판매처 검색과 현재 검색 시점 문구를 확인한다. |
| 6. 해협 상인의 약속 | 거래 기록을 보고하고 상인의 인장을 받는다. 장착 화면에서 적용 지역과 능력을 확인한다. |

첫 완료 보상 초안은 5,000 D와 특수 아이템 ‘해협 상인의 인장’이다. 선단 교역 장비 칸에 장착하며 말라카·자카르타 판매 수령액에 +2%를 적용한다. 기존 판매 보정 상한과 세금·반올림 순서를 공유하고, 교역 견적과 최고가 검색에 같은 금액을 표시한다. 자카르타의 최종 지정 품목은 현행 시장 데이터와 재고 검증으로 확정한다.

말라카 해협의 동서 교역과 여러 문화의 교류를 역사 배경으로 삼는다. 상인·인장·임무는 창작이다. [UNESCO 말라카와 조지타운](https://whc.unesco.org/en/list/1223/)

### 3.3 고급 1 · 마닐라 갤리온의 항로

| 장 | 임무와 이야기 진행 |

첫 완료 보상 초안은 12,000 D와 가상 부선장 이네스다. 동행 시 원양 구간 식량 소모 5% 감소를 적용한다. 선단 평균 보급 계산·장비 중첩·실제 이동·출항 견적이 일치해야 한다. 이네스 고용으로 과거 항해의 식량을 되돌려 주지 않는다.

### 3.5 진행·보상 저장과 효과 연결

- 정적 시나리오 정의와 대화는 별도 카탈로그로 관리한다. 개인 저장에는 이야기 ID·버전·현재 장·완료 단계·선택 분기·미수령 보상 ID·필요한 통과 증거를 넣는다.
- 구매·판매·입항·조사·납품의 기존 성공 처리에 단계 판정을 연결한다. 매 프레임 모든 시나리오를 검사하거나 서버에 진행을 반복 전송하지 않는다.
- 보상용 부선장·아이템은 충돌하지 않는 고정 ID로 기존 명부·가방·수집 카드·능력 설명·장착 슬롯에 연결한다. 주점 소문에서 타입을 미리 구분하지 않는 규칙을 따른다.
- 보상 지급은 개인 저장과 진행 기록을 함께 확정하고, 납품은 화물 차감과 단계 완료를 같은 경제 행동에서 확정한다. 통신 결과가 불명확하면 기존 확인 절차로 재개한다.
- 통과 실적에는 출발 이후 실제 항해 구간·순서·영역 ID만 압축 저장한다. 구조·저장 좌표 보정·북남 경계 연결을 제외하고, 정상 항해의 날짜변경선 통과는 인정한다.
- 고급 이야기의 잠금 화면에 실제 필요한 선박 능력과 준비 상태를 표시한다. 단계 숫자만 만족한 선장이 보급 불가능한 바다로 출항하도록 안내하지 않는다.

## 4. 전 세계 해도·항구 위치 정합성

### 4.1 점검 대상

- 주요 항구 78곳, 보존 항구 112곳 전체의 항구 ID·원래 도시 좌표·현행 접안점·화면 표식·수역·연결 경로를 표로 검사한다. 추가되는 개발 항구와 공동 보급 거점은 등록 상태에 따라 함께 검사한다.
- 현재 해도 원본·정밀 해안선·강 중심선·운하 경로와 항해 격자를 대조한다. 한 화면에서 보이는 바다와 `nav.isLand`·실제 경로의 판정이 다른 지점을 기록한다.
- 아카풀코·시드니를 우선 재현하고 이스탄불·세비야·포르투, 강 항구와 작은 섬 항구를 대표 회귀 구간으로 삼는다. 지도 전체를 고치기 전에 오류 좌표를 특정한다.

### 4.2 수정 원칙

- 설명용 도시 좌표와 실제 접안점을 구분한다. 지도 표식·미니맵·자동 도착·수동 입항·구조 도착·정박한 배는 동일한 접안점을 사용한다.
- 부두를 가장 가까운 아무 바다로 옮기지 않는다. 항구가 있는 해안 방향과 강·만의 연결을 확인한다. 소규모 섬이 원본에서 누락됐다면 표시와 판정에 함께 같은 보완 자료를 적용한다.
- 접안점은 안전한 수역 위에 있고 주변 바다 또는 해당 강의 통행 중심선과 연결되어야 한다. 항로 마지막 구간이 육지를 가로지르거나 표식만 해안에서 멀리 떨어지지 않게 조정한다.
- 수정은 `tools/port-catalog.json` 등 해당 원본과 생성기를 기준으로 한다. 파생 지도·해안 판정·카탈로그·타일이 영향받을 때 필요한 생성기만 실행한다.
- 과거 항구의 방문·소유·발견 ID를 유지한다. 정박 중 저장은 공통 접안점으로 보정하고 항해 중 저장은 현재 위치에서 남은 경로를 재계산한다. 보정만으로 신규 방문·발견·명성·구조비를 만들지 않는다.
- 기존 `navigation-migration.js`가 운하 경유 항해를 건너뛰는 부분도 확인한다. 이미 예약한 통행료·사용한 통행권·현재 운하 통과 상태를 보존하면서 안전한 연결 구간만 재계산한다.

## 5. 직접 조종 입항과 보급 안내

### 5.1 입항 거리 초안

| 수역 | 기존 기준 | 새 검증 시작값 |
| --- | --- | --- |
| 일반 해상 항구 | 최소 30해리, 도시–부두 차이에 따른 확대 | 기본 45해리 |
| 강 항구 | 12해리 | 같은 강 수로 안에서 18해리 |
| 공동 보급 거점 | 10해리 | 연결 수역 안에서 12해리 |
| 출항 직후 재입항 방지 | 입항 범위 밖 추가 8해리 | 해당 입항 범위 밖 추가 12해리 |

도시와 접안점 차이가 큰 항구는 위치부터 수정한다. 예외 반경이 필요한 경우 최대 60해리를 시작 상한으로 검토하고 항구별 이유를 기록한다. 입항과 별개인 항구 정보 발견 거리 80해리는 이번 범위에서 유지한다.

### 5.2 판정과 조작

- 이동 전후 구간과 접안점의 최단 거리를 검사하고 정지 상태에서도 같은 기준을 사용한다. 프레임이 늦어 입항 영역을 한 번에 통과해도 인식한다.
- 우선 가까운 후보만 추린다. 직선으로 안전하게 연결되면 바로 판정하고, 작은 만이나 굽은 하구는 제한된 주변 수역 경로로 연결 여부를 검사한다. 해상은 실제 연결 경로 60해리, 강은 24해리를 초안으로 삼고 육지 너머 지름길을 허용하지 않는다.
- 가까운 다른 항구가 있다는 이유만으로 입항을 막지 않는다. 접근 가능한 후보끼리 도달 순서·연결 거리로 비교하고, 명시적으로 선택한 목적지는 유효 범위 내에서 우선한다. 유효 후보가 여러 개인 곳은 작은 항구 선택 안내를 검토한다.
- 출항한 항구 억제는 실제 출항에만 걸고, 오래 남은 `departedPort` 상태·재접속·운하 이탈이 입항을 막는지 검사한다. 접안 직전 보급 부족으로 출항 검사를 다시 실행해 입항을 거절하는 흐름이 있는지도 확인한다.
- 직접 입항 성공은 기존 `arrive`와 동일하게 정박지·방문·교역 대상·자동 보급을 갱신한다. 짧은 접안 보정 구간 전체의 안개나 발견물을 추가로 공개하지 않는다.
- 변경된 범위를 확인할 수 있도록 선택한 항구 주변 입항 안내를 표시한다. 화면에 안내한 범위와 실제 판정 차이는 수역 연결 조건으로 설명한다.

### 5.3 보급 부족 안내

- 같은 목적지·같은 부족 조건의 안내는 한 장만 유지하고 남은 시간이나 내용을 갱신한다. 다른 목적지나 오류는 구분한다.
- 모바일 방향키·정지 버튼·하단 메뉴·항구 도착 상태를 가리지 않는 위치로 조정하고 짧게 닫힌다. 자세한 부족량은 항로 패널에서 다시 확인할 수 있다.
- 보급이 부족해도 이미 항구 앞에 있는 배의 입항 인식은 수행한다. 직접 조종·자동 출항·구조의 서로 다른 보급 규칙을 같은 오류문으로 처리하지 않는다.

## 6. 가상 세금 징수선

### 6.1 구매와 순회

- 소유 항구 화면에 ‘세금 징수선’을 배치한다. 계정당 1척, 구매가 50,000 D를 초안으로 한다. 구매는 정상 정박·서버 확인 상태에서 진행한다.
- 실제 지도 배·선단 정원·화물·보급·최저 속도에 추가하지 않는다. 항해 중에도 기존 징수선의 업무는 이어진다.
- 구매 후 현실 시간 30분 뒤 첫 항구를 방문하고 이후 항구마다 30분 간격으로 순회한다. 소유 항구 한 곳이면 같은 항구를 30분마다 방문한다.
- 최초 순서는 소유 항구 이름순으로 고정하고 목록을 보여 준다. 각 순회 경계에서 소유권 변동을 반영해 잃은 항구는 제외하고 새 항구는 뒤에 추가한다. 소유 항구가 없으면 대기하며 구매 기록을 보존한다.
- 일정은 서버 기준 현실 시간으로 계산한다. 항해 배속·탭 숨김·컴퓨터 시계 변경이 징수 속도를 높이지 못하게 한다.

### 6.2 징수와 수수료

- 방문한 항구의 해당 선장에게 귀속된 거래 세금과 기본 세수를 합산해 징수한다. 기본 세수의 기존 72시간 적립 한도와 부선장 배정 효과를 적용한다.
- 징수액의 5%를 수수료로 공제하고 95%를 보유 두카트에 지급한다. 총액·수수료·실수령액을 영수증에 표시한다. 징수액 1,000 D이면 수수료 50 D, 실수령 950 D다.
- 정수 두카트 처리에서는 수수료의 1두카트 미만 잔여를 계정에 이월한다. 예를 들어 10 D씩 두 번 징수한 총 수수료도 1 D가 되도록 한다. 빈 항구 방문에는 수수료가 없다.
- 직접 수령과 자동 징수는 같은 장부에서 차감한다. 직접 수령은 징수선 수수료를 붙이지 않는다. 세금 수령을 일반 교역 이익이나 시나리오 납품 실적으로 중복 집계하지 않는다.
- 과거 소유자의 미수령 금액은 현재 소유자에게 지급하지 않는다. 소유권을 잃은 항구의 잔여 귀속액은 기존 직접 수령 경로에 보존한다.

### 6.3 오프라인·동시 처리

- 접속이 끊긴 동안 순회 예정 시각은 진행한다. 실제 지급은 다음 접속 또는 소유 항구 조회 때 확정하며 화면에 마지막 정산 시각을 표시한다.
- 오프라인 중 지난 순회는 같은 항구별 한 번의 합산 정산으로 압축한다. 과거 모든 방문 시각의 세금 잔고를 새로 추정하지 않고 정산 시점에 장부로 확인되는 귀속액만 받는다. 이 방식의 기본 세수 72시간 한도를 구매 화면에도 설명한다.
- 현재 소유권·소유 시작 시각과 예정 방문 시각을 비교한다. 취득 전 예정 방문을 새 소유자의 징수 기회로 소급하지 않는다. 소유 기간의 귀속 세수는 기존 원장이 보존한다.
- 과거 거래에 시각별 원장이 없으므로 예정 시각의 과거 거래 세금을 정확히 재현했다고 표시하지 않는다. 예약 방문과 실제 정산 시간을 구분하고 장부의 현재 값으로 확정한다.
- 항구 장부 차감·돈 지급·수수료 이월·해당 항구의 처리 순번을 원자 변경으로 묶는다. 기존 `atomicAction` 큐와 operation ID 확인 절차를 확장해 재시도·동시 직접 수령·소유권 변경 때 중복 지급을 막는다.
- 소유 항구 요약 `real/ownedPorts`에서 본인 항구만 필터링해 필요한 장부를 읽는다. 필요하면 소유자 쿼리 인덱스를 추가한다. 전체 항구 원문 반복 다운로드와 상시 징수 서버 타이머를 추가하지 않는다.
- 한 번에 최대 10개 항구를 순차 정산하고 이어받기 위치를 저장한다. 실패한 항구의 커서는 확정하지 않고 이미 성공한 항구는 다시 지급하지 않는다. 전투·경제 결과 확인 중에는 완료 뒤 안전하게 재개한다.

### 6.4 화면

구매 전에는 가격·5% 수수료·30분 간격·오프라인 정산·기본 세수 한도를 보여 준다. 구매 후에는 ‘다음 방문 항구 / 남은 시간’, 순회 목록, 최근 20건 영수증과 총 징수액·누적 수수료를 표시한다. 개별 영수증은 정산 시에만 저장하고 초 단위 화면 카운트다운은 브라우저에서 계산한다.

## 7. 주점 완료 표시

- `rumorNote`의 공통 완료 기준을 주점 ‘이 항구에서 만날 사람’ 버튼과 상세 화면에도 적용한다. 소문 버튼에는 이미 완료 상태가 표시되고 있어 그 부분을 중복 구현하지 않는다.
- 아이템은 최초 획득 기록 `acquiredItems`, 부선장은 고용 기록을 사용한다. 소모품 보유량이 0이 되어도 완료 표시를 유지한다. 의뢰 조건 충족만 한 상태는 ‘획득 가능’이며 ‘완료’와 구분한다.
- 아직 소문을 읽지 않은 인물·물품을 새로 노출하지 않는다. 원래 보이는 제목 옆에 공통 ‘✓ 완료’만 붙이고 소문을 탐험·아이템·부선장으로 분류하는 배지를 넣지 않는다.
- 소문노트·주점 목록·항목 상세에서 완료 기준을 공유한다. 주점은 해당 항구 소문만, 전체 소문노트는 읽은 전체 소문만 보여 준다. 노트는 항목을 눌러도 열린 상태를 유지한다.
- 기존 저장에서 명확한 보유·장착·소모 효과·획득 이력으로 확인되는 항목은 복원한다. 조건 달성만으로 실제 획득을 추정하지 않는다.

## 8. 내 배 보기 화면

- 김부장 제안의 ‘매우 돕음’은 메뉴 때문에 현재 배 표시 영역이 좁다는 의미로 해석한다. 첫 화면에서 기함 이미지와 선박 이름·등급·역할·내구도·속도·보급·적재를 우선 배치한다.
- 모바일은 배 이미지가 가로폭을 사용하도록 한 열로 구성한다. 초기 이미지 영역은 가로세로 약 4대3, 최대 높이 280px를 시작값으로 삼고 가로 화면에서는 화면 높이에 맞춘다. 헤더와 이미지가 전체 화면을 고정 점유하지 않게 한다.
- PC는 이미지와 핵심 성능을 나란히 배치한다. 선박 선택은 짧은 목록으로 두고 긴 보유 목록은 해당 영역만 스크롤한다.
- 하단은 ‘선단 / 장비 / 조선·보관’ 탭으로 나눈다. 선택한 선박에 대한 장착·개량·보관·매각을 표시하고, 가격·효과·불가 이유는 관련 행동 가까이 보여 준다.
- 보관선·동행선·기함을 쉽게 구분하고 이미지 옆에서 다른 배를 선택할 수 있게 한다. 탭 변경과 경제 행동 완료 후 선택 배와 스크롤을 가능한 한 유지한다.
- 모바일 360·390·430px, PC 1280px, 가로 화면과 글자 확대에서 이미지·성능·닫기·확인 버튼을 검사한다. 기존 사진 자산과 지연 로딩을 재사용한다.

## 9. 운하 자동 항로와 비용 안내

### 9.1 기존 기능의 미경유 원인 검사

- 코린토스·수에즈·파나마 각각 완공·개방 여부와 `surveyedCanals` 캐시·조회 시점·장거리 worker 전달값을 확인한다.
- `Navigator.routeOcean`의 운하 앵커·양방향 간선·해상 연결·연안 제한이 유효한지 검사한다. 일반 경로와 worker 경로의 선택 결과를 비교한다.
- 항로가 운하를 사용해도 그리기나 안내만 누락된 경우와 실제 우회 경로를 구분한다. 완공 전·미개방·연결 실패를 미경유 오류로 단정하지 않는다.

### 9.2 이용 여부 선택

- 사용자의 후속 결정에 따라 **운하 탭에 ‘자동 항해 시 운하 이용’ 체크박스**를 배치한다. 초기값은 켜짐 초안이며 선택을 계정 설정에 저장해 재접속 때 복원한다. 목적지마다 별도로 운하 이용을 다시 선택하지 않는다.
- 켜져 있으면 현재 이용 가능한 운하를 포함해 목적지까지 유효한 자동 항로를 계산하고, 운하를 경유하는 적절한 경로가 선택되면 자동으로 이용한다. 목적지와 관계없는 운하까지 돌아가는 방식으로 해석하지 않는다. 꺼져 있으면 새 항로에서 운하를 제외한다.
- 항로에는 자동 선택된 경유 운하명·거리·예상 항해 시간·보급·선단 총 사용료를 표시한다. 유료 경유에는 ‘사용료 발생’을 표시하고 무료는 0 D로 표시한다. 별도 ‘이 항로 선택’ 버튼을 매번 누르게 하지 않는다. 일반 경로가 없으면 해당 이유를 안내한다.
- 경로는 현재 선단의 최저 속도·원양 제한·식량·적재 조건으로 검사한다. 비교를 위해 이동 조건을 무시한 경로를 실제 선택 가능한 항로로 제시하지 않는다.
- 지도 항구 클릭·항구 찾기·즐겨찾기·최고가 판매처의 이동·시나리오 출항에서 같은 설정과 견적을 적용한다. 직접 조종 중 목적지 클릭의 자동 항해 전환도 연결한다.

### 9.3 통행료 예약과 통과

- 기존 선박당 통행료와 실제 동행 선박 수를 기준으로 계산한다. 보관선·가상 징수선은 과금 척수에서 제외한다. 운하 통행권 할인과 소모를 견적에 반영한다.
- 운하 이용을 켜 두면 안내된 통행료를 기존 출항 과정에서 자동 예약·정산한다. 운하 이용 여부를 매번 묻는 추가 확인창은 두지 않고, 운하 탭과 출항 견적에 자동 이용·사용료 발생을 명시한다. 통행료가 부족하면 출항을 보류하고 부족액과 설정 위치를 안내한다.
- 기존 예약·통과 확정·미사용 환급 경로를 재사용한다. 통과 전 사용료나 상태가 달라지면 금액을 다시 보여 주고 변경을 확정한다. 더 비싼 유료 경로로 조용히 바꾸지 않는다.
- 중단·목적지 변경·구조·항로 재계산·재접속 때 이미 낸 구간과 미사용 구간을 구분한다. 미사용 예약금과 통행권은 한 번만 환급하고 실제 통과 수입도 한 번만 적립한다.
- 통과 중 토글을 바꾸어 현재 운하에서 순간 이동하지 않게 한다. 설정 변경은 다음 경로 계산부터 적용한다.

## 10. 구매·판매 전량의 거래 시작 단가 적용

- `market-rules.js`의 구매 상자별 단가 증가를 변경한다. 구매와 판매 모두 해당 거래의 수량 전체에 견적 시점 단가를 적용한다.
- 세금·할인 전 거래액은 `시작 단가 × 수량`이다. 세금·아이템·부선장·쿠폰은 기존 계산 순서와 반올림 기준으로 반영한다. 단가 100 D의 상품 50상자는 세금·할인 전 5,000 D다.
- 거래가 성공하면 상품 압력은 실제 수량만큼 변하고 다음 견적에 반영된다. 구매는 상승, 판매는 하락이며 시간 경과 회복과 압력 상한은 기존 규칙을 따른다.
- 취소·재고 부족·자금 부족·적재 초과·서버 거절 거래는 상품 압력·돈·화물·프리미엄 재고를 바꾸지 않는다. 실패한 자동 재시도가 시세를 올리지 않게 한다.
- 기존 견적 유효시간 5초와 항구 revision 비교를 유지한다. 그 사이 다른 거래가 확정되면 새 견적과 총액을 보여 준다. 화면을 오래 열어 둔 과거 단가로 무조건 체결하지 않는다.
- 비교 화면에 현재 단가·수량·세금/할인·최종 합계를 표시하고 ‘거래 완료 후 수량에 따라 다음 시세가 변해요’를 안내한다. 구매 평균 단가는 시작 단가와 일치한다.
- 분할 구매는 각 거래가 다음 시세를 따르므로 한 번에 구매한 총액과 달라질 수 있다. 기존 판매 규칙과 최고가 판매처의 검색 시점 문구는 함께 회귀 검사한다.

### 10.1 대량 거래 후 같은 항구 되팔기 차익 방지 · 사용자 확정

- 사용자는 대량 구매가 끝난 뒤 오른 시세로 같은 항구에 되팔면 차익이 생기는 문제를 지적했다. 공통 가격 압력을 그대로 둔 채 구매 전량 단가만 바꾸면 이 문제가 발생한다. 같은 방식으로 대량 판매로 가격을 내린 뒤 다시 사는 순환도 검사한다.
- 현행 함수로 시각·세금 0·할인 없음·초기 압력 0을 고정해 계산한 예에서는 리스본 와인 시작 구매 단가가 33 D다. 적재 여유가 충분하다고 가정하고 계획대로 1,000상자를 33,000 D에 산 뒤 기존 공통 압력 계산을 적용하면 판매 단가 36 D, 총 36,000 D로 3,000 D 차익이 생긴다. 이는 계산 검증이며 운영 거래를 실행한 결과가 아니다. 시각과 실제 적재·세금에 따라 수치는 달라진다.
- 사용자는 2026-11-13 구매·판매 가격 압력 분리안을 승인했다. 항구·상품별 **구매 가격 압력과 판매 가격 압력을 따로 관리**한다. 구매량은 다음 구매 견적의 상승분에 반영하고 판매량은 다음 판매 견적의 하락분에 반영한다. 내 구매가 판매 견적을 즉시 올리거나 내 판매가 구매 견적을 즉시 낮추지 않게 한다. 두 압력은 각각 현실 시간 경과로 기준값을 향해 회복한다.
- 한 번의 구매·판매 전량에 시작 단가를 적용하는 규칙은 이 보완안과 함께 설계한다. 항구별 지역 가격 차이와 다른 항구로 운송해 얻는 이익을 검증한다. 기존 공통 압력 저장의 이관은 기존 견적 무효화·새 조회 시점 안내와 함께 정한다.
- 매매 가격 차이, 세금, 부선장·장비·할인·쿠폰까지 반영한 수령액으로 같은 항구의 구매→판매와 판매→재구매 순환을 검사한다. 압력 초기값·상한·하한·분할 거래·여러 선장 거래·시간 경과를 포함한다.
- 새 저장은 구매 상승분을 0 이상, 판매 하락분을 0 이하로 별도 기록한다. 기존 공통 압력이 양수이면 구매 쪽으로, 음수이면 판매 쪽으로 이관하고 반대쪽은 0으로 시작한다. 정해진 이관 버전을 한 번만 적용하고 새로고침으로 회복 시각을 초기화하지 않는다.
- 단가 100 D·수량 100상자·세금과 할인 없음 예시에서 구매액은 10,000 D다. 구매 뒤 다음 구매 단가는 상승하고 판매 단가는 기존 88 D를 유지한다. 판매 100상자는 8,800 D이며 판매 뒤 다음 판매 단가만 하락한다. 같은 항구 왕복에서 할인·쿠폰까지 포함한 차익 가능성은 별도 조합 검증으로 확인한다.

| 4 | 운하 경유 검사와 비교·사용료 화면 | `route-planner.js`, `route-worker.js`, `projects.js`, `canal-reservations.js` |
| 5 | 주점 완료 표시·내 배 보기 재배치 | `rumor-ui.js`, `rumor-progress.js`, 선박 화면 생성 코드 |
| 6 | 가상 징수선과 원자 정산 | `port-income.js`, `business-ui.js`, `atomic-account.js`, 소유 요약과 DB 규칙 |
| 7 | 시나리오 진행·대화·보상 공통 처리와 초보 6장 | 정적 스토리 정의, 개인 저장 정규화, 의뢰 패널, 성공 이벤트 연결 |
| 8 | 중급 2편·고급 2편과 부선장·아이템 효과 | 기존 명부·가방·장착·견적·보급·발견 처리 |
| 9 | 기존 저장·동시 처리·화면 통합 검증 | 관련 규칙 테스트, Firebase 에뮬레이터, 로컬 브라우저 |

새 정적 데이터는 필요한 화면에서 불러오고, 지도·소문·시나리오 표시는 기존 캐시와 장부를 활용한다. 징수선은 대상 항구의 경제 쓰기가 추가되고 시나리오는 성공 단계 저장이 추가된다. 실제 비용 증가는 접속·소유 항구·거래 빈도에 달려 있으며 현재 사용량을 확인한 수치로 설명한 것은 아니다.

## 12. 검증과 완료 기준

### 항해·지도

- 전체 112개 접안점의 수역·표식·연결 검사와 주요 78항구의 접근 경로를 검사한다. 개발 항구·보급소는 활성 상태별로 검사한다.
- 시드니·아카풀코·포르투·세비야·이스탄불·강 항구·작은 섬에서 이동 접근·정지 접근·고속 통과·출항 후 재입항을 확인한다.
- 반경 안이어도 육지 반대편·다른 강줄기에서는 입항하지 않아야 한다. 유효 입항 후 구매·판매·보급·자동 보급이 실제 정박 항구에서 활성화돼야 한다.
- 오래된 정박·해상·구조·운하 경유 저장을 새 접안점에 맞추어도 돈·화물·통행료·발견이 중복 변경되지 않아야 한다.

### 경제·징수선·운하

- 1·50·100·최대 허용 상자를 구매·판매해 시작 단가×수량과 다음 시세 변화를 확인한다. 세금·쿠폰·프리미엄 재고·동시 거래 실패를 포함한다.
- 징수선 첫 30분·정확한 경계·항구 한 곳·여러 곳·소유 항구 없음·취득·상실·72시간 초과·연결 중단·수동 수령 겹침을 검사한다.
- 수수료 5%와 잔여 이월, 영수증 합계, 부분 성공 재개, 다른 기기와 소유권 경쟁에서 중복 지급이 없는지 확인한다.
- 운하 3곳 양방향, 열림/닫힘·허용/회피·worker/일반 탐색·여러 척·통행권·요금 변경·환급·재접속을 비교한다.

### 시나리오·주점·화면

- 신규 뗏목으로 초보 30단계를 실제 항해·소량 거래로 완료할 수 있어야 한다. 돈이 드는 소개 화면은 둘러보기로 끝낼 수 있어야 한다.
- 중급 2편과 고급 2편의 장별 시작·목표·완료·중단·재개·최종 보상 수령을 각각 확인한다. 기존 플레이어의 진행 인정과 보상 재지급 방지도 검사한다.
- 보상 능력이 설명·출항 예상·실제 항해·거래·조사에 동일하게 적용되는지 확인한다. 단순 소문 읽기나 조건 충족을 획득 완료로 오인하지 않아야 한다.
- 휴대폰 360/390/430px, PC, 가로 화면, 글자 확대에서 내 배 이미지·입항 안내·대화·항로 비용·조종 버튼의 겹침을 검사한다.
- 구현 시 관련 회귀 검증을 추가하고 `npm test`, 필요한 Firebase 에뮬레이터 규칙 검사, `npm run notes:check`를 실행한다. 문서 작성 단계에서는 게임 테스트를 실행한 것으로 보고하지 않는다.
